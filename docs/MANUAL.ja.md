## 用語集

Qualcomm のスタックは1つのハードウェアに3通りの名前を付けており、SDK・設定ファイル・デバイスパスがそれぞれ別の名前を使うため、本書も3つとも使います。**同じ階層の同義語ではありません**:。README にある「Hexagon NPU」は同じシリコンの対外的な呼び名で、3つとの対応は **NPU**・**Hexagon** の行に書いてあります:

| 用語 | ここでの意味 |
|---|---|
| **HTP** | Hexagon Tensor Processor — アクセラレータそのものと、それを駆動する QNN **バックエンド**の名前。この名を冠するものはバックエンド側の機構です: `libQnnHtp.so`、`htp_backend_ext_config.json`、`QnnHtp.poll`。「HTP」はプロセッサの**種類**であって特定の1個ではありません。 |
| **NSP** | **HTP デバイス1個**、つまり1コア。デュアルNSPのSoCにはこれが2つあります。コアを数えるとき、どちらにモデルが載るかを言うときに使います。 |
| **cDSP0 / cDSP1** | 同じコアの OS 側での名前。デバイスパス(`/dsp/image/dsp/cdsp0`)に現れるのはこちらです。Qualcomm 自身のドキュメントが "CDSP/NSP ID"、"CDSP0/NSP0" と併記しているとおり、**cDSP*n* と NSP*n* は同じコア**です。本書で小文字の `cdsp0` と書いてあるものは常にリテラルのデバイスパスであって、スロット名ではありません(スロットはロールで命名します。下の **スロット** を参照)。 |
| **`device_id`** | どのコアを使うかを選ぶ番号。`0` = cDSP0/NSP0、`1` = cDSP1/NSP1。QNN HTP バックエンドの `devices[0].device_id` そのもので、**配置を実際に決めているのはこれだけ**です。 |
| **NPU** | Neural Processing Unit — この種のアクセラレータを指す業界一般の語。上記シリコンに対する Qualcomm の製品名が **Hexagon NPU** で、README の「Hexagon NPU 上で動く」はこの意味です(= 「QNN HTP バックエンド経由で、その NSP コアのどれかで、HTP 上で動く」)。**スタックの階層ではなく製品名**であり、この名を冠する設定キー・ログ行・デバイスパスは1つもありません。どれを指すのか正確に言う必要があるときは HTP / NSP / cDSP を使ってください。 |
| **Hexagon** | このファミリ全体の土台である Qualcomm の DSP アーキテクチャ。バージョン文字列やパスに現れるのはこちらです: `HEXAGON_VERSION: "v73"`、`ADSP_LIBRARY_PATH` の `lib/hexagon-v73/unsigned`。「Hexagon **NPU**」がアクセラレータ、「Hexagon **v73**」はその中の DSP コアの命令セット版であり、**両者は交換可能な語ではありません**。 |
| **スロット (slot)** | **本サーバ独自の概念**で Qualcomm の用語ではありません: 常駐している1モデルと、その `GenieDialog` ハンドル・ロック・KV状態のまとまり。スロットの `name` はクライアントが使う論理アドレスにすぎず、用途やロール（例: `chat`, `tool_call`, `vision`）を表す名前を付けます。物理コアを固定するのは `device_id` です。 |

以下は Qualcomm 側および本サーバ側の用語です:

| 用語 | ここでの意味 |
|---|---|
| **QAIRT** | Qualcomm AI Runtime — 本サーバがリンクする SDK。QNN と Genie を提供します。 |
| **Genie** | LLM を動かすための QAIRT の C API(`libGenie.so`)。テキストは `GenieDialog_*`、マルチモーダルは `GenieNode_*`/`GeniePipeline_*`。 |
| **`GenieDialog`** | Genie の会話ハンドル1個。ロード済みモデル・KVキャッシュ・サンプラーのまとまりで、スロットごとに1つ持ちます。 |
| **qualla** | `libGenie.so` の内部で、Genie C API と QNN バックエンドの間にある層。SDK のログやエラーメッセージに出てきます。 |
| **モデルバンドル** | デバイス向けにコンパイル済みのモデル一式が入ったディレクトリ: `genie_config.json`、`.bin` のコンテキストバイナリ、トークナイザ、HTPバックエンド拡張設定。`model_root` が指す先です。 |
| **`ctx-bin`** | コンパイル済みの QNN コンテキストバイナリ = バンドル内の `.bin`。**1つのSoC・1つのコンテキスト長向けに**コンパイルされており、跨いで使い回せません。 |
| **コンテキスト長 (CL)** | バンドルがコンパイルされたトークン窓の大きさ。1つのバンドルが複数のコンパイル済みバリアントを持つことがあり、リクエストは収まる最小のものを選びます。 |
| **プレフィル / デコード** | 生成の2つの段階。プレフィルはプロンプト全体を一括処理し、デコードは1トークンずつ吐きます。速度特性が大きく違うため、計測では必ず分離します。 |
| **TTFT** | Time To First Token — リクエストから最初のトークンが出るまでの実時間。実質的にプレフィルの時間です。 |
| **KVキャッシュ** | `GenieDialog` が溜めていくアテンションの key/value 状態。その大きさがスロットの残りコンテキストを決めます。 |
| **prefix キャッシュ** | 繰り返し現れるプロンプト先頭(たいていはシステムプロンプト)の KV キャッシュを本サーバが再利用する仕組み。同じプレフィルを2度払わずに済みます。 |
| **ホットスワップ** | サーバを再起動せずに `POST /v1/models/switch` でスロットのモデルを差し替えること。 |
| **同時常駐 (co-residency)** | 同一デバイス上に2つのモデルを同時にロードしたままにすること。載るかどうかは**バンドルから読み取れるどの数値からも予測できません** — どうエクスポートされたかに依存し、実測するしかありません。[2つのモデルを同時にロードする](#2つのモデルを同時にロードする)を参照。 |
| **w4a16** | 量子化方式の呼び名で、重み4bit・活性化16bit。バンドルがどうコンパイルされたかを表します。 |
| **LoRA** | ロード済みモデルの上に適用する小さなアダプタ。別モデルをロードせずに振る舞いを変えられます。 |
| **VLM** | Vision-Language Model — テキストに加えて画像を受け取るモデル。`GenieDialog` ではなく Genie の composable pipeline を通るため、VLMスロットは別系統で設定します。 |
| **GVM** | Guest VM — ターゲットがベアメタルではなくハイパーバイザ上のゲストとして動いている状態。デバイスレベルの制御の一部がゲストからハードウェアに届かないことがあるため、本書で言及します。 |

## アーキテクチャ概要

- 実装本体はPythonパッケージ `genie_server` で、`genie-server.py` という薄いランチャー、
  またはインストール時に入る `genie-server` コマンドから起動します。リポジトリ上は
  `src/` 配下(`src/genie_server/`)にあり、以下の表のパスはパッケージルートからの表記です:

| モジュール | 役割 |
|---|---|
| `genie_server/config.py` | `env_config.json` のパース、プロセス環境変数の設定 |
| `genie_server/capi.py` | GenieDialog C APIのctypesバインディング(`GenieLib`)+ SDK定数 |
| `genie_server/templates.py` | チャットテンプレート描画(chatml/llama3/llama2/gemma/gemma4)、prefix分割、`/no_think` |
| `genie_server/tools.py` | OpenAI `tools`(function calling)の Hermes 方言: プロンプト生成・出力パース・ストリーミングフィルタ |
| `genie_server/tool_formats.py` | ツール呼び出し方言のレジストリ(Hermes / gemma4)と、スロットがどれを使うかの判定 |
| `genie_server/slots.py` | `Slot`/`SlotManager`: モデルロード、ルーティング、ホットスワップ |
| `genie_server/prefix_cache.py` | ディスク上のKVキャッシュスナップショット |
| `genie_server/engine.py` | 生成エンジン: ロック、ウォッチドッグ、SDKパラメータ、prefixキャッシュ、`finish_reason` |
| `genie_server/vlm.py` | マルチモーダルリクエスト(`GenieNode`/`GeniePipeline`) |
| `genie_server/genie_node.py` | `GenieNode`/`GeniePipeline` composable pipeline APIのctypesバインディング |
| `genie_server/vlm_specs.py` | VLMモデルごとの固有スペック(前処理・ノード構成・プロンプトテンプレート) |
| `genie_server/logprobs.py` | SDKのカスタムサンプラーフック経由のトークンlogprobs(サンプリング/teacher forcingの2モード) |
| `genie_server/protocol.py` | OpenAIワイヤーフォーマットビルダとエラーエンベロープ |
| `genie_server/app.py` | 全FastAPIルート(`create_app`) |
| `genie_server/bootstrap.py` / `asgi.py` | 起動時の配線 / uvicornエントリポイント |
| `tests/` | オフラインテストスイート(`FakeGenieLib` — NPU・`libGenie.so`なしで動作) |

- サーバは1つ以上の**スロット**(`Slot`)から成ります。1スロット = 1つの独立した`GenieDialog`ハンドル + 専用の`threading.Lock` + 専用のトークナイザ/テンプレート/LoRA状態です。`TEXT_SLOTS`を設定しなければスロットは1つ(`"default"`)だけになり、旧バージョンと完全に同じ挙動になります。
- 各リクエストはボディ(または `?model=` クエリ)の `model` フィールドで**どのスロットに送るか**が決まります(`SlotManager.select`)。一致するスロットが無ければ常にプライマリスロットにフォールバックするため、`lm_eval`の固定文字列 `"genie-local"` や単一スロット運用ではクライアント側の変更は不要です。
- スロット内の推論・パラメータ変更・LoRA操作・モデル切り替えは、**そのスロット自身の**`threading.Lock`で直列化されます。**別スロットへの操作はブロックしません** — 2NSP構成では文字通り2リクエストを同時処理できます。
- 各リクエストは呼び出し前に必ず対象スロットの `GenieDialog_reset` を行います。つまり本サーバは**マルチターン会話をSDK側で保持しません**。会話履歴はクライアント側(`messages` 配列)で管理してください。
- ストリーミングは `threading.Thread` + `asyncio.Queue` でCコールバックスレッドとASGIイベントループを橋渡ししています。クライアント切断は `GenieDialog_signal(ACTION_ABORT)` で能動的に中断されます。
- ウォッチドッグ(`threading.Timer`)が `INFERENCE_TIMEOUT` 秒(既定120秒、`env_config.json`で変更可)経過で自動的に推論を中断します。

## SDKの互換性

open-genie-server は `libGenie.so` の薄いクライアントです。したがってその挙動も、
その障害の出方も、**どの QAIRT SDK ビルドで動かしているか**に依存します。

> [!IMPORTANT]
> **既知のSDK欠陥、どのビルドがどれを抱えているか、手元のSDKの確認方法、
> 素のライブラリとリビルド版のどちらを選ぶかは、
> [QAIRT バージョン別の問題点](./QAIRT_VERSIONS.ja.md) にまとめてあります。**
> SDK ビルドを選ぶ前、モデルのエクスポート形式を決める前に読んでください。要点:
>
> - **素の 2.49.x はスロットを壊します** — `prompt_tokens + max_tokens` が
>   `コンテキスト長 − AR_N` を超えたとき。壊したリクエスト自身は 200 で正常に見え、
>   以後そのスロットは、モデルを再ロードするまで全リクエストが失敗します。
>   **本サーバはこれを防ぎません。**
> - **単一コンテキスト長でエクスポートしても消えません** — `[4096]` / AR-128 の
>   バンドルで予算が 384 から 3968 に上がるだけです。
> - **ライブラリをリビルドすれば直りますが、grammar 制約デコーディングを失います。**
>   両方を備えたビルドは存在しません。
> - **`2.49.1.260821` は数字が小さいのに `2.49.40.260810` より新しい**バージョンで、
>   上記のどれも直っていません。

**検証済みの組み合わせ**: QAIRT **2.49.40.260810** および **2.49.1.260821**、
`aarch64-oe-linux-gcc11.2`、SA8255Pボード、Qwen3 w4a16 のコンテキストバイナリ
(`qwen3_0_6b`、`qwen3_4b_instruct_2507`)。加えて **2.48.40.260702**、
`aarch64-android`、同じボードのAndroidゲスト([Androidで動かす](#androidで動かす))。
**2.48 は3つのリセット欠陥をどれも持ちません** — いずれも 2.49 のスケジューラと
ともに入ったものです。ここに挙げた中で、素のライブラリが不利にならない唯一のビルドです。

以降のこの節は欠陥の話ではなく、**エクスポート時の選択** — バンドルにいくつの
コンテキスト長をコンパイルするか — についてです。

### 複数のコンテキスト長で得られるもの

複数のコンテキスト長でコンパイルすることは、楔を露呈させるだけのものではありません。
**SDKはリクエストが収まる最小のバリアントで走らせ、小さいバリアントほどデコードが速い**からです。
単一コンテキスト長のバンドルは、**最初のトークンからフルコンテキスト分のコスト**を払います。

実機で計測(ストリーミングでプレフィル(TTFT)とトークンあたりのデコード速度を分離、
生成120トークン、各3回の中央値):

`qwen3_0_6b` — `context_lengths: [512, 1024, 4096]`:

| プロンプト | +生成 | 有効CL | TTFT | デコード |
|---:|---:|---|---:|---:|
| 34 | 154 | **512** | 82 ms | **68.91 tok/s** |
| 378 | 498 | **512** | 169 ms | **68.84 tok/s** |
| 548 | 668 | **1024** | 253 ms | **59.66 tok/s** |
| 807 | 927 | **1024** | 344 ms | **59.87 tok/s** |
| 980 | 1100 | 4096 | 424 ms | 35.85 tok/s |
| 1754 | 1874 | 4096 | 831 ms | 29.29 tok/s |
| 3903 | 4023 | 4096 | 2017 ms | 29.31 tok/s |

`qwen3_1_7b` — `context_lengths: [4096]`:

| プロンプト | TTFT | デコード |
|---:|---:|---:|
| 33 | 141 ms | **20.49 tok/s** |
| 377 | 330 ms | **20.44 tok/s** |
| 1754 | 1319 ms | **20.42 tok/s** |
| 3904 | 2853 ms | **20.44 tok/s** |

複数コンテキスト長のバンドルは**バリアントごとに平坦域を持ち、境界で段差を作ります** —
最良と最悪で **2.35倍**。単一コンテキスト長のバンドルは、プロンプトを 33 → 3904 トークンに
増やしても **0.3% しか動きません**。

2つのモデルはサイズが違うので、**絶対値ではなく形を読んでください**。0.6B は 4096 バリアントの
中でも `n_past` の増加につれて 35.9 → 29.3 と動きますが、1.7B は動きません — 重みの読み出しが
デコードを支配し、KV側の寄与が埋もれるためです。**だからこそ読むべきは段差であって、
その中のドリフトではありません。**

トレードオフの全体像:

| | 複数コンテキスト長 | 単一コンテキスト長 |
|---|---|---|
| 短いリクエストのデコード | **速い**(ここでは2.35倍) | 常にフルコンテキストのコスト |
| メモリ | バリアントの数だけバッファを持つ | 1組 |
| stock ライブラリでのスロット楔の予算 | **384トークン** | **3968** — 上がるだけで、消えはしない |
| 常駐2モデルの**1本目**として | 余地を残さない | 余地を残す |

短い会話が中心なら、**修正版**ライブラリの上では複数コンテキスト長の方が良い
エクスポートです。一方で素のライブラリでは、短い会話こそ数百トークンで楔に到達する
ケースでもあります。それ以外はすべて逆を指しています —
[ライブラリの選択](./QAIRT_VERSIONS.ja.md#ライブラリの選択)を参照してください。

## マルチテキストスロット

**使える** Hexagon NSP コアが複数あるターゲットでは、`env_config.json` に `TEXT_SLOTS` を設定することで、NSPコアごとに独立したモデルを常駐させ、別スロット宛のリクエストを1つのロックに並ばせずに同時進行させられます。

> [!IMPORTANT]
> **2コアあるかどうかは、SoCの品番で決まる性質ではありません。** 何本使えるかは
> **SKUのライセンスで制限される**ため、外見上同じボードでも1本しか使えないことがあります。
> その場合この節の内容は何も当てはまらず、`device_id: 1` のスロットは割り当て先が
> ありません。以下の実測値は、**ゲストに元のイメージより多くのメモリを割り当てた1台の機体**
> で測ったものです。ここの数値を仕様として読む前に
> [プラットフォーム別の注意点](./PLATFORM_NOTES.ja.md)を参照してください。

**その効果の実測値**([プラットフォーム別の注意点](./PLATFORM_NOTES.ja.md)の機体での測定)。2スロット(cdsp0/cdsp1に同じ `qwen3_0_6b` w4a16)、同一内容のチャットリクエスト8本(SA8255P、QAIRT 2.49):

| | 実時間 | 直列比 |
|---|---|---|
| 1本ずつ・1スロット | 8.06秒 | — |
| 2本同時・**同じ**スロット | 8.09秒 | 1.00倍 — 設計どおりスロットのロックで直列化される |
| 2本同時・**1本ずつ別スロット** | 6.13秒 | **1.31倍** |

スロットが実際に重なって動いているのは確かです(同一スロットの行が対照実験で、こちらは
まったく速くなっていない)。ただし2つ目のNSPで得られるのは**2倍ではなく約1.3倍**で、
両方が動いている間は1リクエストのレイテンシが 1.0秒 → 1.5秒 に伸びます。生成トークン数を
増やしても1.33倍、2スロットのCPUマスクを分離しても(両方が `0xe0` を継承する代わりに
`0x30`/`0xc0`)1.38倍、さらにサーバのCPU使用率が約260%→約12%に下がる `poll: false` でも
1.31倍のままでした(後述の `QnnHtp.poll` の節)。**ホスト側CPUが頭打ちの原因ではありません**。
API より下の層で2つのNSPが何かを共有している(メモリ帯域が有力)と考えられます。

**足りないスループットがどこへ行っているか。** 各リクエストをプレフィル(TTFT)と
デコード(残り)に分けて測ると、この2つは並列時にまったく違う振る舞いをする —
`qwen3_0_6b`、生成64トークン、5回の中央値:

| プロンプト長 | | TTFT | プレフィル | デコード |
|---|---|---|---|---|
| 33 | 単独 | 0.048秒 | 686 tok/s | 68.7 tok/s |
| 33 | 両スロット稼働 | 0.058秒 | 570 tok/s | 44.1 tok/s |
| 121 | 単独 | 0.053秒 | 2263 tok/s | 68.8 tok/s |
| 121 | 両スロット稼働 | 0.065秒 | 1863 tok/s | 44.1 tok/s |
| 249 | 単独 | 0.093秒 | 2668 tok/s | 69.1 tok/s |
| 249 | 両スロット稼働 | 0.110秒 | 2264 tok/s | 43.9 tok/s |

並列時、各スロットは**プレフィル性能を83〜85%維持するのに対し、デコードは64%しか
維持しない**(どのプロンプト長でも同じ)。これはメモリ帯域律速の典型的な兆候である:
プレフィルは各重みをプロンプト全位置で再利用する(計算律速)のに対し、デコードは
**1トークンごとに全重みを読み出す**(帯域律速)ため、デコード同士は競合し、
プレフィル同士はほとんど競合しない。概算では、4bit重み約0.3GB/トークン × 68.7 tok/s ≒
**単独 約21 GB/s**、2スロット合計で **約26 GB/s** で頭打ち。

この分解は実測値を予測する: デコード支配の負荷なら 2 × 0.64 = **1.28倍**(実測1.31倍)、
プレフィル支配なら 2 × 0.83 = **1.66倍**。実際に249トークンのプロンプト +
`max_tokens: 1` で確かめると **1.64倍**だった。

**つまり2つ目のスロットの価値はワークロードの形で決まる。** 長いプロンプト+短い出力
(分類・抽出・スコアリング・RAGのリランク)なら1.6倍近くまで伸びる。チャット的な
短いプロンプト+長い出力なら約1.3倍。表の再現は
`tests/integration/measure_ttft_tps.py`。

容量設計は**1.3倍**で見積もり、2つ目のスロットは「スループットが倍になる仕組み」ではなく
**別のモデルを同時常駐させる手段**、あるいは**1本の長いリクエストが他の全クライアントを
止めないようにする手段**として捉えてください。

```json
{
  "QAIRT_SDK_ROOT": "/home/root/qairt/2.49.40.260810",
  "HEXAGON_VERSION": "v73",
  "MODELS_BASE_DIR": "/home/root/models",
  "PREFIX_CACHE_DIR": "/home/root/prefix_cache",
  "TEXT_SLOTS": [
    {"name": "tool_call", "device_id": 0, "model_root": "qwen3_1_7b-genie-w4a16-qualcomm_sa8775p"},
    {"name": "chat", "device_id": 1, "model_root": "qwen3_4b_instruct_2507-genie-w4a16-qualcomm_sa8775p"}
  ]
}
```

- `name`: スロットの論理識別名（クライアントからのルーティングやログ用。例: `tool_call`, `chat`）。`POST /v1/models/switch` の `slot` フィールド、`?slot=`/`?model=` クエリで参照する。
- `device_id`: QNN HTPバックエンドの `devices[0].device_id`(0=cDSP0, 1=cDSP1 …)。SA8255Pは `dsp_arch: v73`。
- `model_root`: そのスロットが起動時にロードするモデルディレクトリ(`genie_config.json` を含む)。

> **2スロットが必ず載るとは限らない。** 上の構成が起動するかどうかは、各スロットが
> どのモデルをロードするか、そして**配列に並べた順（ロード順）**に依存する。
> 小さいモデル（例: 単一CL 1.7B）を先に、大きいモデル（例: 4B）を後にロードする必要があり、
> 逆に4Bを先にロードすると2本目が `err 1002` で失敗する。**2スロット構成を決める前に次の節を読むこと。**

### 2つのモデルを同時にロードする

2本目のスロット(`TEXT_SLOTS`を2要素にする、または`TEXT_SLOTS`と`VLM_SLOTS`を併用する)を
設定すると、起動時に次のエラーで失敗することがある:

```
[ERROR] "Could not create context from binary for context index = N : err 1002"
[ERROR] Startup failed: GenieDialog_create failed: -1
```

`err 1002`は`QNN_COMMON_ERROR_MEM_ALLOC`。1本目は正常にロードされ、**2本目がコンテキスト
生成の途中で失敗する**。**サーバ側で事前に判定することはできない** — 予算を報告するAPIが
存在しないため、実際にその組み合わせを試すまで分からない。

以下はすべて1台のボード(SA8255P / デュアルNSP / 12.3GB、QAIRT 2.49.40.260810、
`0001`+`0003`パッチ適用済み`libGenie.so`)での実測値。**具体的なモデルサイズは制約の
「形」を示す例であって、そのまま他環境に移せる数値ではない。**

> **この制約は「モデル」だけでなく「どうエクスポートされたバンドルか」でも動く。**
> 下記のうち2本を後から**単一コンテキスト長で再エクスポート**したところ、
> それまで失敗していた組み合わせが載るようになった。両方の表を残し、
> 各行がどちらのバンドルでの実測かを明記してある。
> **測っていないバンドルに行を持ち込まないこと。**

#### はっきり言えること

**テキストモデル2本の場合、ロード順で決まる。** **3つのコンテキスト長でコンパイルされた
バンドル**(`context_lengths: [512, 1024, 4096]`)に対して9通りの起動構成を実測した。
**同じ2モデルでも、どちらを先に生成するかだけで成否が反転する**:

| ロード順(先 → 後) | `device_id` | 合計パラメータ | 結果 |
|---|---|---|---|
| 0.6B → 0.6B | 0, 1 | 1.2B | OK |
| 0.6B → 0.6B | 0, **0** | 1.2B | **err 1002** |
| 0.6B → 1.7B | 0, 1 | 2.3B | OK |
| **1.7B** → 0.6B | 0, 1 | 2.3B | **err 1002** |
| 0.6B → 1.7B | **1, 0** | 2.3B | OK |
| 1.7B → 1.7B | 0, 1 | 3.4B | **err 1002** |
| **4B** → 0.6B | 1, 0 | 4.6B | **err 1002** |
| 0.6B → **4B** | 0, 1 | 4.6B | OK |
| **1.7B** → 4B | 0, 1 | 5.7B | **err 1002** |

この表から、全実行で例外なく成り立つ事実が4つ得られる:

1. **合計サイズは判定基準ではない。** 0.6B + 4B(合計4.6B)は載るのに、
   1.7B + 1.7B(合計3.4B)は載らない。**大きい方の組が通っている。**
2. **`device_id`も判定基準ではない。** どちらのNSPに割り当てるかを入れ替えても結果は
   変わらない(3行目と5行目は同じ組をコアを逆にしただけで、どちらもOK)。
   ピン留めはコアを選ぶだけで、**予算を分割しない**。
3. **「1本目に何をロードするか」で決まる。** 0.6Bを1本目にした構成は**すべて成功**し、
   それより大きいものを1本目にした構成は**2本目が何であれすべて失敗**した。
   **これらのバンドルでは**閾値は0.6Bと1.7Bの間にあった。**3サイズしか試していないので、
   それ以上には絞り込めていない。**
   **この閾値はモデルだけで決まる性質ではない — 次の表を参照。**
4. **2本目は別のNSPに置く必要がある。** 表の中で同一デバイスの構成だけが失敗した。
   この実行は**同じモデルを2回**ロードしており、生成されるHTP拡張設定が
   `"context": {"weight_sharing_enabled": true}` を持つため、当初は
   weight sharing の競合が原因である可能性を排除できていなかった。**現在は排除済み。**
   電源サイクル直後から**別モデル同士**で取り直すと、0.6B → 1.7B は
   `device_id` 0 と **0** で `context index = 2 : err 1002`、同じ組み合わせを
   0 と **1** に置くと両スロットがロードされ生成もできる。2本目の確保シーケンスは
   両者で**バイト単位に同一**(276,431,360 / 8 buffers)で、違いは `device_id` だけである。
   したがってこれは weight sharing ではなく**コアあたりの上限**である。
   その上限が何で決まるかは未解明 — 0.6B + 0.6B も 0.6B + 1.7B も同じく1コアでは落ちるので
   **1本目だけで上限に達している可能性**があるが、これより小さいバンドルが無いため詰められていない。

**単一コンテキスト長でエクスポートすると閾値が上がる。** 1.7B と 4B を後から
単一コンテキスト長(`context_lengths: [4096]`、エクスポート時のツールチェーンも
QAIRT 2.45.0 → 2.49.0 に変化)で再エクスポートした。0.6B はそのまま。
同じ起動構成を測り直した結果:

| ロード順(先 → 後) | 1本目のバンドル | 2本目のバンドル | 合計 | 以前 | **現在** |
|---|---|---|---|---|---|
| 0.6B → 0.6B | 複数CL | 複数CL | 1.2B | OK | OK |
| 0.6B → 1.7B | 複数CL | 単一CL | 2.3B | OK | OK |
| 0.6B → 4B | 複数CL | 単一CL | 4.6B | OK | OK |
| **1.7B → 0.6B** | **単一CL** | 複数CL | 2.3B | **err 1002** | **OK** |
| **1.7B → 1.7B** | **単一CL** | 単一CL | 3.4B | **err 1002** | **OK** |
| 1.7B → 4B | 単一CL | 単一CL | 5.7B | err 1002 | err 1002 |
| 4B → 0.6B | 単一CL | 複数CL | 4.6B | err 1002 | err 1002 |

規則の「形」は変わっていない(**1本目が大きいほど2本目に許される上限が下がる**)。
**動いたのは閾値**である。以前は「1本目は0.6Bでなければならない」だったが、現在は:

- 1本目 0.6B → 2本目は 4B まで載る
- 1本目 1.7B → 2本目は 1.7B まで載る(4B は載らない)
- 1本目 4B → 2本目は 0.6B すら載らない

**反転した2行は、再エクスポートした1.7Bを1本目にした2行そのもの**であり、
単一コンテキスト長のバンドルは1本目として確保する量が少ない、という理解と整合する。
**ただし証明ではない。** 再エクスポートではコンテキスト長の数だけでなく
ツールチェーンのバージョンも変わっており、**4Bも単一コンテキスト長になったが1本目としては
依然として何も載せられない**。さらに 1.7B の `Allocated total size` はこの変更で
**264MB → 276MB とむしろ増えている**のに、挙動は改善している。
なお単一コンテキスト長のバンドルには
[スロットが壊れる問題の予算を引き上げる](./QAIRT_VERSIONS.ja.md#単一コンテキスト長は予算を引き上げるが欠陥を消しはしない)
という別の利点もあるので、どちらにせよ選ぶ理由がある。

**ロードできるだけでなく、動作も確認済み**: 単一コンテキスト長の1.7Bを2本常駐させた状態で、
両スロットが応答し、`"slot"` によるルーティングも正しく、
**同時2リクエストが8.32秒(単独は5.90秒)= 1.42倍**だった
([並列性の実測](#マルチテキストスロット)と同水準)。

**ホストのメモリ不足でも断片化でもない** — 少なくともテキストモデル2本の場合は。
失敗した瞬間の状態:

```
/proc/buddyinfo order-10 = 4MBブロックが993個空き(約4GBの連続領域)
MemAvailable  12.29 GB / 12.66 GB
CmaFree       95 MB / CmaTotal 100 MB   (CMAは未使用)
```

**4GBの連続領域が空いている状態で276MBの確保に失敗している。**
さらに**再起動直後**(4MBブロックが約18倍潤沢な状態。長時間テスト後の156個に対し2818個)
でも同じ組が同じ地点で失敗した。→ **枯渇しているのはcDSP側の資源で、Linuxゲストからは
観測できない。**

**ただし大きいモデルは実際にホストメモリを消費する。** 単体ロード時:

| モデル単体 | `MemAvailable` | order-10ブロック |
|---|---|---|
| 0.6B テキスト | 12.27 GB | 179 |
| 1.7B テキスト | 12.29 GB | 993 |
| **4B テキスト** | **7.87 GB** | **0** |
| **約4B VLM** | **6.91 GB** | **15** |

4B級のモデルは**再利用不可のメモリを4〜5GB**消費し、大きいブロックのプールを枯渇させる。
一方、小さい方は測定できるほどの消費がない。**これらはサーバプロセスのRSSには現れない**
(VLMロード時でも170MB)。DMA-BUF経由の確保だからである。したがって**4B級同士の組では
ホスト側の枯渇も原因の一部である可能性がある** — 小さいモデルの組では原因でないことが
実証されているにもかかわらず。

**テキストモデルと約4BのVLMは同居できる — ただしテキスト側が単一コンテキスト長で、
両者が別のコアにいるとき。** これは結論の反転である。複数コンテキスト長のテキストバンドルでは
どちらの順でも失敗し(positional-encodingバリデータフラグをクリアしてもしなくても)、
それは**今日でも変わらない**。0.6Bを単一コンテキスト長で再エクスポートして測り直すと:

| テキストバンドル | `SLOT_LOAD_ORDER` | text `device_id` | VLM `device_id` | 結果 |
|---|---|---|---|---|
| **単一CL `[4096]`** | `text-first` | 0 | 1 | **成功 — 両スロット ready・両方が応答** |
| **単一CL `[4096]`** | `vlm-first` | 0 | 1 | **成功** |
| 単一CL `[4096]` | `text-first` | 0 | **0** | `err 1002`(context index 1) |
| 複数CL `[512,1024,4096]` | `text-first` | 0 | 1 | `err 1002`(context index 3) |

**ロード順は関係なく、`device_id` を分けることが効く** — テキスト2本の表と同じ「同一コアは不可」の規則である。
ロードできるだけでなく動作も確認済み: テキスト/VLM を交互に4ラウンド + 同時1組、すべて正しく応答した。

**これは、この節が長らく欠いていた対照実験そのものである。** 0.6Bは両方の形のバンドルが手元にあるため、
**コンテキスト長の数以外はすべて固定**できる(同じVLM、同じコア、同じ順序、同じライブラリ、同じセッション)。
それで結果が反転する。さらに重要なのは、**2つのテキストバンドルの確保量がバイト単位で同一**である点だ:

```
単一CL 0.6B :  Allocated total size = 275120640 across 3 buffers  -> VLMが載る
複数CL 0.6B :  Allocated total size = 275120640 across 3 buffers  -> err 1002
```

VLM側の確保シーケンス(348,520,576 / 8 buffers)も両者で同一である。
つまり **`err 1002` が数えているのは確保バイト数ではない** — バンドルが持つコンテキスト長バリアントの数、
すなわち**生成されるQNNコンテキストの本数**に比例する何かである(ここでは2グラフ対6グラフ)。
**バンドルのサイズからは事前に判断できない**ということでもある。

> **判定は必ず電源サイクル直後の初回起動で行うこと。** 起動に失敗するとデバイスが片付かず
> (`Failed to deregister opPackages ... err 6020`、`Failed to teardown transport layer: 1004`
> がpdIdごとに大量に出る)、以後の試行ほど不利になる。実際、電源サイクル直後には成功した同じ構成が、
> 失敗した起動を2回挟んだ後には context index 1 で落ちた。**上の表はすべて電源サイクル直後の初回**である。

[スロット生成順](#スロット生成順slot_load_order)と
[`examples/config/env_config.text-vlm.sample.json`](../examples/config/env_config.text-vlm.sample.json)を参照。

#### はっきり言えないこと

- **計算式は無い。** パラメータ数・ディスク上のサイズ・合計サイズ・libGenieログの
  `Allocated total size`のいずれも結果を予測しない。特に**このログ行は誤解を招く** —
  0.6Bで262MB、1.7Bで264MBとほぼ同じ値を報告するが、この2つは1本目に置いたときの挙動が
  まったく違う。**この値はI/Oバッファであって重みではない。**
  最も強い例は上のテキスト+VLMの組で、**同一モデルの2つのバンドルがバイト単位で同じ値を報告する**のに、
  片方はVLMの居場所を残し、もう片方は残さない。
- **メカニズムは不明。** `err 1002`はDSP側の確保が失敗したと言っているだけで、
  ゲストの`/proc`のどこにもその分は現れない。**SDKソースまで追っていない。**
- **なぜ「小さいモデルが先」だと通るのかは説明できていない。** 1本目の`GenieDialog`が
  DSP側の予算の大半を予約してしまう、という挙動と整合的ではあるが、
  **結果からの推測であって観測したわけではない。**
- ~~**コンテキスト長の数がどれだけ効いているかは切り分けられていない。**~~
  **テキスト+VLMの組については切り分け済み。** 0.6Bを両方の形でエクスポートして
  両方のバンドルを保持しているため、ツールチェーンを含む他の条件をすべて固定できる。
  その状態で、**コンテキスト長の数だけで**VLMが隣に載るかどうかが決まる(上の表)。
  ただし**テキスト2本の行については依然として間接的** — こちらのバンドルは新しい
  ツールチェーンで再エクスポートされており、同等のA/Bが無い。
- **具体的な数値が他のSoC・他のメモリ搭載量・他のQAIRTバージョンに当てはまるかは不明。**
  1台のボードでの実測にすぎない。

#### 実務上の指針

- **スロットは小さい順に並べる。** `TEXT_SLOTS`では配列の先頭に最小のモデルを置く。
  テキスト+VLM構成では`"SLOT_LOAD_ORDER": "text-first"`を設定し、
  (小さい方の)テキストモデルを先に生成させる。
- **単一コンテキスト長でエクスポートしたバンドルを優先する。** 1.7B同士はそれで同居でき、
  複数コンテキスト長のときはできなかった。**テキストモデルとVLMが同居できるのもこの形のときだけ**である。
  **再エクスポートしたら測り直すこと** — 今回、バンドルを作り直したら載る組み合わせが変わった。
- **テキスト+VLM構成では**、テキスト側を単一コンテキスト長のバンドルにし、2つのスロットを
  別の`device_id`に置く。
  [`env_config.text-vlm.sample.json`](../examples/config/env_config.text-vlm.sample.json)から始めるとよい。
- **同居の判定は電源サイクル直後の初回起動で行う。** 起動失敗はデバイスを汚し、以後の試行すべてを歪める。
- **デュアルNSPでは各スロットに異なる`device_id`を割り当てる。**
- **限界は実測で決めるしかない。** 実際に試し、サーバが起動して両スロットが`ready`を
  報告すれば成功。**事前に確認する手段は無い。**
- **起動時の`err 1002`はDSPの固着ではない。** クリーンな失敗であり、プロセスは終了して
  資源を掴んだままにはならない。**スロットの順を入れ替えて再起動するのが安全で、
  最初に試すべきこと。**
- **モデルの消費量を測るには**: 単体でロードして`MemAvailable`と`/proc/buddyinfo`を見る。
  **`MemFree`の差分は使わないこと** — モデルファイルがpage cacheに乗って信号を埋もれさせる
  (0.6Bが1.7Bより多く消費しているように見えることがある)。
  どちらの指標も**実際に失敗しているDSP側の確保は捉えていない**ので、あくまで参考値。

### デバイスの固定方法(`slots.pin_htp_device`)

各モデルの `genie_config.json` の `dialog.engine.backend.extensions` が指すHTPバックエンド拡張設定ファイル(例: `htp_backend_ext_config.json`、QNNの `"devices":[{"device_id":N,...}]` スキーマ)を、**モデル本体には一切手を加えず**、スロットごとにコピー→`device_id`を上書き→`PREFIX_CACHE_DIR/.htp_ext_cache/<slot名>_<元ファイル名>` として保存し、そのコピーを参照するように起動時のGenie設定を書き換えます。そのため:

- 同じモデルディレクトリを複数スロットに割り当てても、元の設定ファイルは汚染されません。
- モデル側の `genie_config.json` に `extensions` が無い(HTPバックエンドを使わない、等)場合は `device_id` 指定を無視し、警告ログを出してそのまま起動します(NSPの固定は行われず、バックエンドの既定デバイスが使われます)。
- `device_id` を指定しない(`TEXT_SLOTS`を使わない、または `"device_id": null`)場合はこの処理自体スキップされ、モデル自身の設定ファイルがそのまま使われます(従来通り)。
- `device_id` は起動時に検証されます。0〜7 の整数か、未指定のいずれかでなければならず、文字列・小数・負値はスロット名つきのエラーで拒否され、HTP設定には書き込まれません。**これはタイプミス除けであってハードウェアの確認ではありません** — そのSoCに実際にいくつHTPデバイスがあるかはダイアログ生成時までQNNしか知らないため、NSPが1個の環境で `"device_id": 1` を指定した場合は従来どおりそこで失敗します(`GenieDialog_create ... err 1002`)。

### ADSP_LIBRARY_PATH

DSP側のskelライブラリ検索パスは、実際に使われている `device_id` の集合から動的に組み立てられます(例: `device_id` に0と1が両方あれば `/dsp/image/dsp/cdsp0;/dsp/image/dsp/cdsp1` を含める)。`TEXT_SLOTS` 未設定時は従来通り `cdsp0` のみです。

### ルーティング

| 操作 | スロット選択方法 | 未指定/不一致時のフォールバック |
|---|---|---|
| `/v1/completions`, `/v1/chat/completions` | body の `model`、または body の `slot`(スロット**名**)で上書き | プライマリスロット(`slots[0]`) |
| `/v1/prefix/warmup`, `/v1/lora/*` | body の `model` | プライマリスロット |
| `/v1/server/performance_policy`(GET) | クエリパラメータ `?model=`(`?slot=` は不可) | プライマリスロット |
| `/v1/lora/current` | クエリパラメータ `?slot=`(スロット**名**)、無ければ `?model=` | プライマリスロット |
| `/v1/server/idle` | クエリパラメータ `?slot=`(スロット**名**) | プライマリスロット |
| `POST /v1/models/switch` | body の `slot`(スロット**名**、モデルIDではない) | プライマリスロット |

`model` によるルーティングは「現在そのスロットにロードされているモデルの `active_model_id`(= モデルディレクトリ名)と完全一致するか」で決まります(`SlotManager.select`)。`POST /v1/models/switch` だけは対象が「これからモデルを入れ替えるハードウェアスロット」そのものなので、モデルIDではなく**スロット名**で選びます。

2つのスロットが同じモデルディレクトリをロードしている場合(`active_model_id`が同一になり`model`では区別できない — [制約事項](#制約事項)参照)、`/v1/completions`/`/v1/chat/completions`のbodyに明示的に`"slot": "<名前>"`を指定すればそのスロットを直接指定できます。指定時は`model`によるルーティングより優先されます。

### モデルパスの解決ルール

**相対パス**の `model_root` は `MODELS_BASE_DIR` 配下として解決されます(上の例は `/data/models/qwen3-4b-htp` をロードします)。**絶対パス**の場合は基準を無視してそのまま使われるので、基準ディレクトリの外にあるバンドルを読ませたいときはこちらを使います。`MODELS_BASE_DIR` が未設定のとき、相対パスはサーバの作業ディレクトリ基準になります — これは**どこから起動したかに依存する**ので、相対パスを使うなら基準は設定しておいてください。

`POST /v1/models/switch` の `model_dir` も同一のルールで解決します。したがって `{"model_dir": "llama3-8b-htp"}` と `model_root: "llama3-8b-htp"` は同じディレクトリを指します。**同じ名前は同じモデル**であり、起動時にロードされたか後から切り替えられたかで変わりません。

**この基準は閉じ込め(sandbox)ではありません。** 絶対パスの `model_dir` は意図的に配下の外からもロードできます — `MODELS_BASE_DIR` はパスを短く書くためのものであって、稼働中のサーバが開けるディレクトリを制限するものではありません。

これは**見落としではなく決定です**。計測器である以上、誰かが `/tmp` に置いたばかりのバンドルを指せる必要があり、閉じ込めるということは**測る前に必ず登録させる**ということだからです。ただし結果ははっきり書いておきます — **認証も無いので、ポートに到達できる者は誰でも、サーバプロセスが読めるあらゆるパスを開かせられます。** [README](../README.ja.md#このプロジェクトの目的)のとおり、**自分で管理しているネットワークで動かしてください。**

### genie_config.json との関係

各スロットの `model_root` 直下の `genie_config.json` は Genie SDKの `GenieDialogConfig_createFromJson` にそのまま渡されます(`device_id` 指定時はHTP拡張設定のコピーのみ差し替え)。サーバは以下のパスだけ、モデルディレクトリからの相対パスとして解決・存在確認します(`slots.load_dialog_config`):

- `dialog.tokenizer.path`
- `dialog.engine.backend.extensions`
- `dialog.engine.model.binary.ctx-bins`(配列)
- `dialog.context.grammar.file`(設定されている場合。[Grammar制約デコーディング](#grammar制約デコーディング)参照)
- `dialog.embedding.lut-path` と `dialog.perlayer-embedding.lut-path`(設定されている場合。Gemma系バンドルが持ちます。Qwen3 のエクスポートにはありません)
- `dialog.engine.model.binary.lora.adapters[].bin-sections[]`(設定されている場合。LoRAアダプタの重み)
- `dialog.ssd-q1.forecast-prefix-name`(設定されている場合。投機デコードの forecast prefix。**これだけは `engine.model.binary` の下ではなく `dialog` の直下**です)

いずれかのファイルが見つからない場合、起動時ロードは `sys.exit(1)`、`/v1/models/switch` 経由のロードはHTTP 500エラーになります(サーバ自体は落ちません)。

**なぜ解決が必要か**: SDKはこれらを素のファイルハンドルで開くため、バンドル内の**相対パス**はモデルディレクトリではなく**サーバの作業ディレクトリ**を基準に解決されます。しかもエラーメッセージはそのどちらも示しません — LUT が無いときは `"Embedding File not present."`、forecast prefix が開けないときは「キャッシュが壊れている」ように見えるメッセージが出ます。先に `model_root` 基準で解決しておくことで、どこから起動してもバンドルが動きます。

#### `QnnHtp.poll` はCPUを約260%使うが、ここでは何の得も無い

手元のモデルバンドルは `dialog.engine.backend.QnnHtp` に `"poll": true` を持っており、
HTPバックエンドがDSPの完了をブロックせずビジーウェイトする設定になっている。
SA8255P(QAIRT 2.49)で同一内容の64トークン生成を25回、1スロットでの実測:

| モデル | `poll` | レイテンシ(中央値) | スループット | サーバプロセスのCPU |
|---|---|---|---|---|
| `qwen3_0_6b` | `true` | 0.961秒 | 66.6 tok/s | **約263%** |
| `qwen3_0_6b` | `false` | 0.951秒 | 67.3 tok/s | **約12%** |
| `qwen3_4b_instruct_2507` | `true` | 5.738秒 | 10.6 tok/s | **約260%** |
| `qwen3_4b_instruct_2507` | `false` | 5.731秒 | 10.6 tok/s | **約3〜12%** |

**レイテンシは誤差の範囲で同じ、CPUは約20分の1**。2スロット同時実行にも影響しない
([マルチテキストスロット](#マルチテキストスロット)の1.31倍は `poll: false` でも同じ値)。
これは同時に、あの1.31倍の頭打ちがホスト側CPUのせいではないことの裏付けにもなっている。

**計測で理由を示せない限りポーリングは切ること。** 共有デバイス上では、
飽和した3コアはシステム上の他の処理から奪ったものになる。バンドルを編集してもよいが、
他人のモデルディレクトリに触らずにサーバ側で上書きすることもできる:

```json
{
  "MODELS_BASE_DIR": "/home/root/models",
  "POLL": false,
  "TEXT_SLOTS": [
    {"name": "tool_call", "device_id": 0, "model_root": "qwen3_1_7b-genie-w4a16-qualcomm_sa8775p"},
    {"name": "chat", "device_id": 1, "model_root": "qwen3_4b_instruct_2507-genie-w4a16-qualcomm_sa8775p", "poll": true}
  ]
}
```

`POLL` が全スロットの既定値で、スロット個別の `poll` がそれを上書きする。
**どちらも未設定なら何も変えない**ので、既存のデプロイは従来どおりの挙動になる。
この上書きは**スロットの属性**なので、`/v1/models/switch` で別モデルに切り替えても維持される。
VLMスロットは参照しない。

一度だけ観測して再現しなかった注意点: `poll: false` で**起動直後の1リクエストだけ**
中央値の2倍かかったことがある(続く26リクエストは全て互いに0.01秒以内)。テールレイテンシが
重要な用途なら、この表を鵜呑みにせず自分で測ること。


## 起動方法

インストールしてもしなくても動きます:

```bash
pip install .[logprobs,vlm]      # 開発中は -e . でも可
```

配布名は `open-genie-server`、import するパッケージ名は `genie_server` で、
インストールすると `genie-server` コマンドが入ります。インストールしない場合も、
リポジトリ直下のランチャーが自分で `src/` を `sys.path` に足すので、
クローンしたままで動きます。`genie_server/` を `genie-server.py` の隣にコピーした
配置でも同様です。ランチャーは「インストール済みパッケージ → 隣の `genie_server/`
→ `src/`」の順に探すので、どちらの配置でも動きます。当方のボードはリリース版の
wheel を venv に入れ、`genie-server` コマンドで起動しています。**避けるべき配置は
1つだけ** — インストール済みパッケージとディレクトリコピーを併存させることです。
コピーがインストール済みパッケージを隠してしまい、どちらが動いているのか
分からなくなります。

```bash
genie-server                     # インストール済みの場合
python3 genie-server.py          # クローンから、または実機上で
# 既定で 0.0.0.0:8080 で待受
python3 genie-server.py --config /path/to/env_config.json --host 0.0.0.0 --port 8080
```

またはuvicornから直接(設定パスは`GENIE_SERVER_CONFIG`環境変数、既定`./env_config.json`):

```bash
GENIE_SERVER_CONFIG=env_config.json uvicorn genie_server.asgi:app --host 0.0.0.0 --port 8080 --workers 1
```

**`--workers` は必ず1にしてください。** 各スロットの `GenieDialog` ハンドルはプロセス内グローバル状態であり、複数ワーカープロセスに分割すると別々のNPUコンテキストの取り合いになり破綻します。

## Androidで動かす

本サーバはAndroidターゲットでもそのまま動きます。プラットフォームを意識する必要が
あったコードは、`libGenie.so` をどのQAIRT ABIディレクトリから読むかと、
`ADSP_LIBRARY_PATH` をどう組み立てるかの2箇所だけです。`TARGET_PLATFORM` を設定する
(または `"auto"` のままにする)以外、設定は同じです。

SA8255PのAndroidゲスト(Android 15、arm64-v8a、root shell)で、素のQAIRT 2.48
`aarch64-android` と Qwen3-0.6B w4a16 バンドルを使って検証しました。実機統合テストは
**22 pass / 3 fail / 14 skip**。3件の失敗はいずれもlogprobsで、numpyが入っていないため
サーバが事前に拒否したものです([入らないもの](#androidで入らないもの)参照)。

### プラットフォームで変わるもの

| | `linux-oe` | `android` |
|---|---|---|
| QAIRT ABIディレクトリ | `lib/aarch64-oe-linux-gcc11.2`(glibc) | `lib/aarch64-android`(bionic) |
| `ADSP_LIBRARY_PATH` | SDKのskel群、`/usr/lib/rfsa/adsp`、使用中の`device_id`ごとの`/dsp/image/dsp/cdspN` | `/vendor/lib/rfsa/adsp` を**先頭**に、続いてSDKのskel群。`cdspN` は付けない |
| `LD_LIBRARY_PATH` | サーバは設定しない | SDKのABIディレクトリ + `/vendor/lib64` |

一方のABI向けにビルドしたライブラリはもう一方では読み込めません。OE Linux用に
リビルドした `libGenie.so` をAndroidで使うことはできず、逆も同様です。

> [!IMPORTANT]
> **自動車向けターゲットでは、DSP側のC++ランタイムを手で配置する必要があります。**
> `libc++.so.1` と `libc++abi.so.1` を、SDKの `lib/hexagon-<ver>/unsigned/` ディレクトリに
> コピーしてください。これが無いと、あらゆるdialogの生成が
> `Failed to create device: 14001` で失敗し、**ログには他に理由が何も出ません**。
> 実体はQNXの主VMにありますが、同じボードでLinuxゲストも動いているなら、
> そのゲストの `/dsp/image/dsp/cdsp0/` から取れます(同一ファイルです)。
> これは Android Automotive に対する Qualcomm の要件であって、本サーバ固有の話ではありません。

### Pythonランタイムをデバイスに載せる

AndroidにはPythonが入っておらず、python.orgの公式Androidリリースは**組み込み用**の
配布です。`libpython3.x.so` と標準ライブラリは含まれますが、**インタプリタの実行ファイルは
入っていません**。その `libpython` に対してNDKでクロスコンパイルした、`Py_BytesMain()` を
呼ぶだけの約5kBのランチャを用意すれば、通常のコマンドラインインタプリタになります。

ゲストには通常ネットワーク経路が無いので、ホスト側でホイールを集めて
`pip install --no-index --find-links=<dir>` で入れてください。`ensurepip` は
オフラインで動くので、pip自体のブートストラップはこれで足ります。

### Androidで入らないもの

本サーバの依存のうち3つは、Androidホイールを公開していません。`tokenizers` は
extras ではなく本体側の依存なので、そのままではpipがインストール自体を拒否します。
本体を `--no-deps` で入れ、入るものだけを個別に入れてください
(`[logprobs]` と `[vlm]` は丸ごと諦めることになります):

| | 影響 |
|---|---|
| `numpy` | **logprobsとプロンプトスコアリングが HTTP 400 を返します。** サーバは起動時にnumpyの有無を確認し、生成の途中で失敗する代わりに明示的なメッセージで拒否します。 |
| `tokenizers` | トークン数が `len(text.split())` にフォールバックします。単語を空白で区切らない言語では致命的にずれ、しかも報告される usage だけでなく**コンテキストチェックと既定の `max_tokens` にも効きます** — [トークン数のカウント](#トークン数のカウント)参照。 |
| `pillow` | VLMスロットが使えません(VLMには`numpy`も必要です)。 |

`pydantic-core` もAndroidホイールを公開していません。pipはこれを黙って回避して
pydantic 1.x に後退し「解決成功」と報告しますが、現行のFastAPIはpydantic v2を要求するため
**import時に落ちます** — pipが成功と言った解決をそのまま信用してはいけません。
NDKとmaturinで `aarch64-linux-android` 向けに `pydantic-core` をクロスビルドすれば
動くホイールが得られます。同じくRust製の `tokenizers` にも同じ手が使えるはずです。


## チャットテンプレートの選択ルール

`format_chat_prompt` / `split_prompt_for_prefix_cache` が使うテンプレート(`llama3` / `llama2` / `chatml` / `gemma` / `gemma4`)は、**リクエストの `model` フィールドではなく、選択されたスロットが実際にロードしているモデル**(`slot.chat_template`)から決まります。

判定順序(`_detect_template`、スロットごとに起動時/切り替え時に一度だけ実行):

1. `env_config.json` の `CHAT_TEMPLATE` が設定されていればそれを使う(全スロット共通)。
2. 未設定なら、そのスロットのモデルディレクトリ名を小文字化し、
   - `"llama3"` または `"llama-3"` を含む → `llama3`
   - `"llama2"` または `"mistral"` を含む → `llama2`
   - `"gemma4"` または `"gemma-4"` を含む → `gemma4`(**先に判定される**。下記参照)
   - `"gemma"` を含む → `gemma`(Gemma 2/3系。systemロールが無く、systemテキストは最初のuserターンに前置、assistantロール名は`model`)
   - それ以外 → `chatml`(Qwen等はここに該当)

> **注意**: 以前のバージョンはリクエストの `model` フィールドで判定していましたが、`lm_eval` はモデル名に関わらず常に固定文字列 `"genie-local"` を送るため、実際には常にChatML分岐に落ちるバグがありました。現在は選択されたスロットの状態のみで決まります。リクエストの `model` フィールドは(1)どのスロットにルーティングするかの選択、(2)レスポンスへのecho、の2用途にのみ使われ、テンプレートは選択しません。

テンプレートに応じたプロンプト形式:

| テンプレート | 形式 | Prefix キャッシュ分割 |
|---|---|---|
| `llama3` | `<\|begin_of_text\|><\|start_header_id\|>role<\|end_header_id\|>\n\ncontent<\|eot_id\|>...` | 可能(system メッセージのみprefix化) |
| `llama2` | `<s>[INST] <<SYS>>...<</SYS>>...content [/INST] ... </s>` | **不可**(systemが`[INST]`に融合するため) |
| `chatml` | `<\|im_start\|>role\ncontent<\|im_end\|>\n...` | 可能 |
| `gemma` | `<bos><start_of_turn>user\n...<end_of_turn>\n<start_of_turn>model\n` | **不可**(systemは最初のuserターンに融合) |
| `gemma4` | `<bos><\|turn>system\n...<turn\|>\n<\|turn>user\n...<turn\|>\n<\|turn>model\n` | 可能(system が独立したターンのため) |

> **なぜ gemma4 を別系統にしているか。** Gemma 2/3 との違いが2つあり、どちらも実害があります:
>
> 1. **ターンの区切りが `<\|turn>` と `<turn\|>`(ID 105 と 106)** で、
>    `<start_of_turn>` / `<end_of_turn>` ではありません。しかも
>    **Gemma 2/3 の綴りは gemma4 の語彙に存在しません** — そのまま書くと1マーカーあたり
>    約9個の通常トークンに分解されます。`gemma4-e2b-it` での実測では、同じ質問のプロンプトが
>    `gemma` テンプレートで39トークン、`gemma4` で22トークンでした。品質も変わり、
>    あるテスト問題は旧綴りでは終端しないリストに退化し、新綴りでは正常に答えました。
> 2. **`system` が独立したターン**であり、最初の user ターンには融合しません。
>    これは Google 自身のテンプレートの挙動で、Gemma 2/3 と違って
>    **gemma4 が prefix キャッシュを分割できる理由**でもあります。
>
> またこの種のバンドルは `genie_config.json` の `eos-token` 配列に **`106` を含める必要があります**。
> 含めないと生成がモデルのターン終端を越えて続き、`<turn\|>` が本文に漏れます。
> `eos-token` はサーバではなく**バンドル側の設定**です — 応答に `<turn\|>` が繰り返し現れたら、
> まずこの配列を疑ってください。
>
> **gemma4 のツールマーカーは独自のもので、サーバはそれを話します。**
> ツール呼び出しは `<\|tool_call>call:NAME{...}<tool_call\|>`、宣言は
> `<\|tool>declaration:NAME{...}<tool\|>`、応答は
> `<\|tool_response>response:NAME{...}<tool_response\|>` で、文字列引数は
> JSON のクォートではなく `<\|"\|>` で囲みます。このテンプレートのスロットは、
> Hermes 形式の `<tool_call>` JSON ではなくこの方言でツール呼び出しを
> 宣言・解析・再描画します — [`TOOL_FORMAT`](#設定-env_configjson) と、
> ストリーミングの違いを説明している
> [Function calling](./API.ja.md#function-calling-tools) を参照してください。
>
> まだ使っていないマーカーが1系統あります: 推論
> (`<\|channel>thought...<channel\|>`)です。`enable_thinking` は Qwen3 の
> `/no_think` ソフトスイッチであり、本サーバに gemma4 版の相当物はありません。
> gemma4 バンドルはバンドル自身の既定の思考モードのままになります。

## Prefix KVキャッシュ

`messages` に `system` ロールが含まれ、かつテンプレートが分割可能(llama3/chatml/gemma4)な場合、system プロンプト部分だけを別途KVキャッシュとして保存・復元します。

- キャッシュキー: `sha256(f"{slot.name}|{slot.active_model_id}|{slot.active_lora_adapter}\x1f{prefix_prompt}")[:16]`
- **スロット/モデル/LoRAでnamespace化**されているため、`/v1/models/switch` や `/v1/lora/apply` で状態を切り替えても、別スロット/別モデル/別LoRA用に保存されたKVキャッシュを誤って復元することはありません(単にキーが変わるため自然にmiss扱いになります)。
- 保存形式: `GenieDialog_save`/`GenieDialog_restore` が書き出すファイル(またはディレクトリ)を `PREFIX_CACHE_DIR/prefix_<key>.geniestate` として管理(全スロット共通のディレクトリですが、キーが分かれているため衝突しません)。

フロー:

```
MISS: GenieDialog_reset → query(full_prompt, SENTENCE_COMPLETE, cb)  (自動的にはキャッシュされない)
HIT:  GenieDialog_reset → GenieDialog_restore → query(remaining, SENTENCE_END, cb)
ウォームアップ(POST /v1/prefix/warmupのみ): GenieDialog_reset → query(prefix, SENTENCE_BEGIN, noop) → GenieDialog_save
```

通常の`/v1/chat/completions`/`/v1/completions`でのMISS時は**キャッシュへの書き込みは行われません** — 単にfull_promptを1回の`SENTENCE_COMPLETE`クエリとして実行するだけです(`engine.py` の共通生成パス。キャッシュ対象外のリクエストと同じ経路)。上記のBEGIN+`GenieDialog_save`の2段階プライミングは、明示的に`POST /v1/prefix/warmup`を呼んだ場合のみ実行されます。その後、同じprefixに一致するリクエストが来ればHITします。

### コストと損益分岐

SDKは `GenieDialog_save`/`_restore` を**まったくプロファイルしていない**
(該当するイベント種別が無く、`apply-engine-state-time` は別経路
`qualla/dialog.cpp:2653` のもの)。そのためサーバ側で両方を計測し、
[`GET /v1/server/profile`](./API.ja.md#get-v1serverprofile) の `host_measured`
としてSDK自身の数値とは分けて返している。

SA8255P・`qwen3_4b_instruct_2507` での実測(3回の中央値、`max_tokens: 4`):

| システムプロンプト | MISS時TTFT | HIT時TTFT | 削減 | 復元 | 保存(warmup時1回) |
|---|---|---|---|---|---|
| 36 トークン | 183.5 ms | 181.8 ms | 1.7 ms | 2.7 ms | 20 ms |
| 72 トークン | 185.1 ms | 184.9 ms | 0.2 ms | 3.8 ms | 47 ms |
| 135 トークン | 360.4 ms | 183.7 ms | **176.7 ms** | 5.4 ms | 95 ms |
| 270 トークン | 537.3 ms | 184.1 ms | **353.2 ms** | 9.0 ms | 198 ms |
| 477 トークン | 712.2 ms | 183.5 ms | **528.7 ms** | 14.7 ms | 353 ms |

**復元はほぼ無料**(3〜15ms、状態サイズに応じて緩やかに増える)。損益を決めるのは
復元コストではなく **AR-128 のプレフィルバッチ**([プロファイリング](#プロファイリングsdk側のkpi)参照)。
HITはバッチ単位でプレフィルを丸ごと消すので:

> **prefix cache が得になるのは、システムプロンプトが単独でプレフィルバッチを
> 占めるだけの長さになってから — 本モデル群では約128トークン以上。**
> それ未満だとシステムターンは残りのプロンプトと同じバッチに同居するため、
> HITしても削減はほぼゼロで、数msの復元コスト分だけ小さく損をする。

非対称性に注意: **保存は復元の5〜25倍のコスト**(20〜353ms)。ただし1プレフィックスにつき
1回、warmup時に、リクエスト経路の外で払われる。

## Grammar制約デコーディング

Genie SDK(qualla)は `basic` dialog(大半のバンドルが宣言する型)でgrammar制約デコーディング(XGrammarバックエンド)をサポートしています。JSON Schema/正規表現/EBNFのいずれかで出力を制約し、無効なトークンをロジットマスキングで排除します(jump-forward高速化込み)。

> [!WARNING]
> **制約を実際に適用するのは `basic` dialog だけです。** grammar オブジェクトを
> 生成するのは基底の `Dialog` なので、どの dialog 型でも文句を言わずにロードされますが、
> サンプリングした logits に `maskLogits` を掛けているのは `dialogs/basic.cpp` だけです。
> `ssd-q1`(投機デコード)バンドルに `grammar` ブロックを付けると、モデルはロードされ、
> 設定の検証も通り、ログにも何も出ず、**出力は制約されません**。SDK もサーバも
> それを教えてくれないので、制約された応答を信用する前にバンドルの `dialog.type` が
> `basic` であることを確認してください。

**重要な制約: これはモデル/スロット単位で固定される機能であり、リクエストごとに切り替えることはできません。** Genie SDKの公開C API(`GenieDialog.h`)にはgrammarを実行時に設定・変更する関数が一切無く(`GenieDialog_setValue`のような汎用setterも存在しない)、grammarは`GenieDialog_create()`が内部でDialogを構築する際に`genie_config.json`から一度だけ読み込まれます。変更するには`GenieDialogConfig`からDialogを作り直す必要があり、これは`/v1/models/switch`と同等のコスト(モデル再ロード)です。

OpenAI APIの`response_format`のようにリクエストごとに異なるスキーマを渡す用途には使えません。「常にJSON Schema Xに従って出力するモデル」を専用スロットとして用意する、という使い方をしてください。

### 設定方法

`genie_config.json`の`dialog.context`に`grammar`ブロックを追加します:

```json
{
  "dialog": {
    "context": {
      "size": 4096,
      "grammar": {
        "backend": "xgrammar",
        "type": "json-schema",
        "file": "grammar_schema.json"
      }
    }
  }
}
```

| フィールド | 値 | 備考 |
|---|---|---|
| `backend` | `"xgrammar"` 固定 | SDKが実装しているのはXGrammarのみ。他の値を指定すると`GenieDialog_create`が失敗する(起動時はサーバも起動失敗、`/v1/models/switch`経由ならHTTP 500) |
| `type` | `"json-schema"`(既定)/ `"regex"` / `"ebnf"` | スキーマの種類 |
| `file` | モデルディレクトリからの相対パス(または絶対パス) | **スキーマ/パターン/文法定義そのものを書いたテキストファイル**(ファイル名やヘッダではなく内容が使われる)。`slots.load_dialog_config`が他のアセットパスと同様に解決・存在確認する |

`tokenizer-json`フィールドは**設定しないでください**。SDK側で非推奨・無視される扱いになっており(ボキャブラリはロード済みの生トークナイザから自動的に導出される)、設定しても効果が無いまま警告ログが出るだけです。

### XGrammarが入ったライブラリが必要

**素の** `libGenie.so`(`lib/aarch64-oe-linux-gcc11.2/`)にはXGrammarが静的リンクされているため、上記の設定はそのまま動作します。

> [!IMPORTANT]
> **SDKのソースからリビルドした `libGenie.so` にはgrammarバックエンドが一切入りません** — スロット恒久故障の本質的な対策として[QAIRT バージョン別の問題点](./QAIRT_VERSIONS.ja.md#選択肢1--修正した-libgenieso-を使うgrammar-が不要なら推奨)が推奨している修正版も同様です。そのライブラリでは、`grammar` ブロックを持つ `genie_config.json` のモデルをロードした時点で `GenieDialog_create failed: -1` となり、ログに `"Grammar backend configured but qualla was built without ENABLE_GRAMMAR"` が出ます(起動時なら起動失敗、`/v1/models/switch` 経由ならHTTP 500)。メッセージが示すリビルドフラグが役に立たない理由と、手元のライブラリを1行で判定する方法は、対処1の警告を参照してください。

### 実機で確認できたこと、および既知の欠陥1件

素の 2.49.40.260810(SA8255P、`qwen3_0_6b` w4a16)では、3種別いずれも出力が正しく制約され、`stream: true` との併用も `logprobs` との併用も動作します。

一方、3種別すべてに影響するSDKの欠陥が1件あります: **応答の末尾にモデルの終端トークンがそのままテキストとして付きます**(ChatMLモデルなら `<|im_end|>`)。制約された部分自体は正しい — JSONオブジェクトは完結しスキーマにも適合し、正規表現も厳密に一致します — が、この末尾のマーカーのせいで、JSON Schema制約の応答は `json.loads()` で解析できず、正規表現制約の応答は自分のパターンに一致しません。**サーバ側では除去していません**。本機能を使うクライアント側で末尾の特殊トークン文字列を取り除いてください。本件は再現プログラムと修正案を添えてQualcommへ報告済みです。

## プロファイリング(SDK側のKPI)

`GENIE_PROFILE: true` を設定すると各テキストスロットに `GenieProfile` ハンドルが
バインドされ、`GET /v1/server/profile` でそのスロットの**直近クエリについてSDK自身が
計測した値**が取れます(ホスト側の時間計測は一切含みません):

```bash
curl "$base_url/v1/server/profile?slot=chat"
```

```json
{
  "slot": "chat",
  "model": "qwen3_4b_instruct_2507-genie-w4a16-qualcomm_sa8775p",
  "summary": {
    "prompt_tokens": 25.0, "ttft_ms": 184.599, "prefill_tokens_per_s": 135.4,
    "generated_tokens": 32.0, "decode_tokens_per_s": 11.01, "generation_ms": 2815.63
  },
  "profile": { "header": {...}, "components": [ ... ] }
}
```

`summary` は dialog のKPIを馴染みのある単位に平坦化したもの、`profile` はSDKのJSONそのもの
(`GenieDialog_create` の初期化時間や、該当経路を通ったときの `apply-engine-state-time` /
`lora-adapter-switch-time` も含む)。

**これは意図的にOpenAI APIの外に置いています。** プロファイリングの有無にかかわらず
chat/completions のレスポンス形状は一切変わりません — クライアントはその形状を検証しますし、
本サーバはOpenAI外のものを全て `/v1/server/` 配下に置く方針だからです。

| | |
|---|---|
| 有効化 | env_config.json の `"GENIE_PROFILE": true` |
| 実行時の切り替え | **不可**。プロファイラは `GenieDialog_create` の前に dialog *config* へバインドされる(`GenieDialog.h:216`)ため再起動が必要。無効時 `GET` は HTTP 409 |
| 対象 | テキストスロットのみ。`/v1/models/switch` をまたいで維持される(ハンドルはスロットの属性) |
| 保持 | SDKは**直近1クエリ**の値のみ保持(`last_usec`)。系列が必要ならリクエストごとに取得すること |
| コスト | 計測可能な差は無し(有効時3.017秒 vs 無効時3.014〜3.015秒) |

同一リクエストでのホスト側計測との突き合わせ(4B、プロンプト25トークン、生成32):
SDK側は TTFT 184.6ms・デコード 11.01 tok/s、クライアント側の総時間は3.017秒に対し
SDK側合計は 0.185 + 2.816 = 3.001秒 → **1リクエストあたり約16msがHTTP・テンプレート・
ctypesのオーバーヘッド**という内訳になります。

## VLM(マルチモーダル)対応

`genie_server/genie_node.py`(`GenieNode`/`GeniePipeline` ctypesバインディング、汎用プラミング層)と
`genie_server/vlm_specs.py`(モデル固有の前処理・ノード構成・プロンプトテンプレート)を介して、
Qwen3-VLのような画像入力モデルに対応する。**テキスト専用の`Slot`/`GenieDialog`経路とは
完全に別のサブシステム**であり、既存のテキスト専用エンドポイントの挙動には一切影響しない。

`numpy`/`Pillow`が無い環境では自動的に無効化され(起動時ログに警告、`VLM_SLOTS`は無視)、
サーバはテキスト専用として起動する。

### 設定方法

`env_config.json`に`TEXT_SLOTS`と並列の`VLM_SLOTS`キーを追加する:

```json
{
  "VLM_SLOTS": [
    {"name": "vision", "device_id": 0, "model_root": "/models/qwen3-vl", "spec": "qwen3_vl"}
  ]
}
```

`model_root`直下には`genie-app-script.txt`が想定するファイル一式(`img-enc-htp.json`,
`text-encoder.json`, `text-generator.json`, `vision_encoder.bin`, 各`ctx-bins`,
`embedding_weights.raw`, `tokenizer.json`)に加えて、位置エンコーディング/attention mask用の
`sample_inputs/{position_ids_cos,position_ids_sin,full_attention_mask,window_attention_mask}.raw`
が必要(固定解像度前提で起動時に一度だけ読み込み、以後の全リクエストで使い回す — 詳細は
`genie_server/vlm_specs.py`の`VLMSpec.static_tensor_files`)。`device_id`が指定されている場合、`Slot`と
同じ仕組み(`slots.pin_htp_device`)で各ノードのHTP拡張設定を書き換えてNSPピン留めする。

`spec`は`vlm_specs.VLM_SPECS`のキー(既定・現状唯一の実装は`"qwen3_vl"`)。別モデル/別
解像度エクスポートに対応する場合は`genie_server/vlm_specs.py`に新しい`VLMSpec`を追加登録する
(GenieXの`core/` vs `models/*.h`分離と同じ発想 — このファイル以外は変更不要)。

### スロット生成順(`SLOT_LOAD_ORDER`)

`TEXT_SLOTS`と`VLM_SLOTS`の両方が空でない場合にのみ意味を持つ。QAIRT 2.49では
**どちらの順にも別々の落とし穴がある**ため、固定せず設定キーにしてある:

| 値 | 動作 |
|---|---|
| `"vlm-first"`(既定) | VLMスロットを生成してからテキストスロットをロード |
| `"text-first"` | テキストスロットをロードし、**バリデータフラグをリセットしてから**VLMスロットを生成 |

**リセットが必要な理由**: `pos-id-dim`/`rope-theta`を使うテキストモデルの`GenieDialog`を
生成すると、libGenie内部の**プロセスグローバルな**staticフラグ2つが立つ。
`pipeline::TextGenerator`は`GenieDialogConfig_createFromJson`を経由せず
`Dialog::validateDialogConfig()`を直接呼ぶためこのフラグをクリアせず、以降のVLM
text-generatorノードが必ず
`Specify one config from pos-id-dim and positional-encoding`で弾かれる。
`"text-first"`では両フェーズの間で`GenieLib.reset_dialog_validator_flags()`を呼び、
**フラグをリセットする唯一のAPI**経由でクリアする。

**`"text-first"`を使いたくなる理由**: **テキストモデル2本**のとき、デュアルNSPのターゲットでは
2つが同時に載るかどうかが**どちらを先に生成したか**で決まる。大きいモデルを先に生成すると、
`device_id`をどう割り当てても2本目の`GenieDialog_create`が`err 1002`
(`QNN_COMMON_ERROR_MEM_ALLOC`)で失敗する。小さいテキストモデルを先にロードすることが
その同時常駐の前提になる。
「どこから大きすぎるか」は、**1本目をどうエクスポートしたか**にも依存する:
同じモデルでも、単一コンテキスト長のバンドルの方が複数コンテキスト長のものより
2本目に残す余地が大きい。
**テキスト + VLM**の組では順序は効かないことが分かった(下の注記)ので、
そちらでの`"text-first"`は単に無害な既定値である。

> **SA8255P(QAIRT 2.49)での実測**: 約4Bの`qwen3_vl_4b_instruct`はテキストモデルと**同居できる**。
> ただし**テキスト側が単一コンテキスト長でエクスポートされており、かつ2つのスロットが
> 別の`device_id`にあるとき**に限る。その条件下では**どちらの順でも成功する**ので、
> 決めているのは`SLOT_LOAD_ORDER`ではなく**バンドルの形**である。
> 複数コンテキスト長のテキストバンドルではどちらの順でも載らず、これが以前の版に書かれていた内容である。
> テキストモデル同士も同居する: 0.6B + 4B、および**単一コンテキスト長のバンドルでは**
> 1.7B + 1.7B と 1.7B + 0.6B。
> まず[2つのモデルを同時にロードする](#2つのモデルを同時にロードする)を読むこと
> (この制約について**分かっていること/分かっていないこと**をまとめてある)。

### リクエスト形式

`POST /v1/chat/completions`にOpenAI形式の`content`配列(`image_url`パート含む)を送ると、
自動的にVLM経路にルーティングされる(`model`フィールドで対象スロットを選択するルールは
テキストスロットと同じ — `_select_vlm_slot`。bodyに明示的に`"slot": "<名前>"`を指定すれば
テキストスロットの`/v1/completions`/`/v1/chat/completions`と同様に上書きできる —
[マルチテキストスロット](#マルチテキストスロット)参照。同じモデルディレクトリを複数の
`VLM_SLOTS`エントリにロードしている場合に必要(`_select_vlm_slot_for_request`)。
存在しない名前は`404`):

```json
{
  "model": "vision",
  "messages": [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user", "content": [
      {"type": "text", "text": "What is in this image?"},
      {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,<...>"}}
    ]}
  ],
  "stream": true
}
```

1メッセージに複数の`image_url`パートを含めることもできる(テキストと画像を交互に並べた
セグメント列として、Qwen3-VLの`<|vision_start|>`/`<|vision_end|>`込みで
`vlm_specs.qwen3vl_build_prompt_segments`が組み立てる)。

### 生成トークン数の上限

VLMリクエストの`max_tokens`は**反映できない**。`GenieNode.h`/`GeniePipeline.h`には
リクエスト単位のトークン上限も中断APIも無く、テキストコールバックの戻り値も捨てられるため、
生成の途中でパイプラインを止める手段が一切ない。SDKが用意している唯一の上限は
text-generatorノードの`max-num-tokens`で、これはGenieが**ノード生成時に一度だけ**読む。
サーバはこの値を`VLM_SLOTS[].max_tokens`から埋める:

```json
{
  "VLM_SLOTS": [
    {"name": "vision", "device_id": 0, "model_root": "/models/qwen3-vl",
     "spec": "qwen3_vl", "max_tokens": 1024}
  ]
}
```

| 値 | 挙動 |
|---|---|
| 省略 | **1024**(既定値) |
| 正の整数 | そのトークン数で生成を打ち切る |
| `0` | **上限なし** — モデルがEOSを出すか、コンテキストを使い切るまで生成し続ける |

ノード生成時に焼き込まれる値なので、変更するには`env_config.json`を編集して
**サーバを再起動する**必要がある。実行時に変更するエンドポイントは無く、そのスロットの
全リクエストに一律で適用される。実際に効いている値は起動ログで確認できる:

```
VLM slot 'vision' ready: model=qwen3-vl device_id=0 spec=qwen3_vl max-num-tokens=1024
```

上限なしの場合は`max-num-tokens=(uncapped)`と出る。

#### 上限を外すと実際どうなるか

モデルが短く答えないプロンプト(「できるだけ詳しく説明して」など)を投げると、
コンテキストを使い切るまで生成し続ける。Qwen3-VL 4B(コンテキスト4096、約14 tok/s)で
同一プロンプト・同一画像を実測した結果:

| `max_tokens` | 実時間 | 生成トークン数 |
|---|---|---|
| `1024` | 72秒 | 1024 |
| `0`(上限なし) | **318秒** | 約3800(コンテキスト枯渇) |

この318秒の間そのVLMスロットのロックを保持し続け、**クライアントが切断しても止められない**。
他のリクエストは全て待たされる。出力もコンテキストが尽きた時点で文の途中で切れる。
上限を上げればその分だけ時間が延び、外した場合の1リクエストの上界はコンテキスト長だけになる。

意図的にモデルの出せる最長の回答が欲しく、かつそのスロットを他と取り合わない場合にのみ
`max_tokens`を`0`にすること。それ以外では上限を残す。

#### `finish_reason`

どちらの上限で止まった場合も`finish_reason`は`"length"`になる。EOSによる自然終了だけが
`"stop"`:

| 生成の終わり方 | `finish_reason` |
|---|---|
| モデルがEOSを出した | `stop` |
| `VLM_SLOTS[].max_tokens`に到達 | `length` |
| コンテキストを使い切った(上限なし、またはコンテキストより大きい上限) | `length` |

コンテキスト枯渇で終わった場合もHTTPは`200`で、そこまでに生成されたテキストを返す。
切り詰められたことはエラーではなく`finish_reason`で伝える。なお`usage.completion_tokens`は
実際に生成された数なので、`max_tokens`が無視される以上、クライアントが要求した値を
超えることがある。

### V1のスコープ外(既知の制約)

`GenieNode.h`/`GeniePipeline.h`には`GenieDialog`にある以下のAPIが**存在しない**ため、
VLM経路では以下がサポートされない:

- **リクエスト単位の`max_tokens`/`stop`**: SDKレベルで強制する手段が無い。指定しても無視される
  (`GenieDialog_setMaxNumTokens`/`setStopSequence`相当が無い)。生成長はスロット単位で
  制限する — [生成トークン数の上限](#生成トークン数の上限)を参照。
- **クライアント切断時の中断**: `GeniePipeline_execute()`はブロッキング呼び出しで、
  開始したら自然終了まで止められない(`GenieDialog_signal`相当が無い)。切断後もサーバ側では
  推論を最後まで実行し続け、そのVLMスロットのロックは自然終了まで保持される。
- **マルチターン会話**: 常に単発(`pipeline.reset()`をリクエストごとに呼ぶ)。会話履歴は
  保持されない。
- **`/v1/models/switch`によるホットスワップ、LoRA、Prefix KVキャッシュ、grammar制約**:
  いずれも`GenieDialog`専用APIか、V1では未実装。
- **リモートURL画像の取得**: `data:`(base64)形式のみ対応。`http(s)://`等は明確に400エラー
  (組み込み/自動車向けサーバから予期しない外部通信を行わないため)。

## トークン数のカウント

トークン数はモデル自身のトークナイザ(`genie_config.json` が指すパスを `tokenizers` パッケージで読み込んだもの)で数えています。この値は3か所で使われます: レスポンスの `usage`、長すぎるプロンプトを400で弾く**コンテキスト超過チェック**、そして `max_tokens` 未指定時の既定値(コンテキストサイズ − プロンプト長)です。

**`tokenizers` が未インストールの場合、この3つとも `len(text.split())` にフォールバックします。** 単語を空白で区切る言語なら妥当な近似ですが、区切らない言語ではまったく役に立ちません。Qwen3 のトークナイザとの実測比較:

| サンプル | 実際のトークン数 | `split()` | ずれ |
|---|---:|---:|---:|
| 英語の段落 | 43 | 33 | 1.3倍 |
| 日本語の段落 | 55 | **1** | 55倍 |
| 日本語・4段落 | 216 | **1** | 216倍 |
| 中国語の文 | 24 | **1** | 24倍 |
| タイ語の文 | 35 | 3 | 12倍 |
| 韓国語の文 | 30 | 8 | 3.8倍 |
| 空白の無いJSON | 17 | **1** | 17倍 |

単語間に空白を置かない言語は**おおむね1文=1トークン**として数えられ、詰めて書かれたJSONのツール呼び出しペイロードは、どれだけ長くても1トークンになります。

影響は `usage` の値が狂うだけでは済みません:

- **コンテキスト超過チェックが機能しなくなります。** 本当にコンテキスト窓を超えているプロンプトが数トークンとして数えられ、チェックを通過してSDKまで届きます。これはまさにこのチェックが防ぐべき失敗そのもので、モデルは生成する余地が無いまま `finish_reason: "length"` の空応答を返し、呼び出し側には理由が分かりません。
- **`max_tokens` の既定値がコンテキストのほぼ全体になります。** 「コンテキストサイズ − プロンプトのトークン数」で計算しているため、プロンプトを過小に数えると、すでに使い切っているはずの分を生成予算として渡してしまいます。
- **トークン数を数える下流の処理がすべて狂います。** `lm_eval` の集計や、呼び出し側が独自に載せているコスト計算・クォータ管理などが該当します。

**VLMスロットもテキストスロットと同じ基準で数えます。** composable pipeline はホスト側にトークナイザオブジェクトを公開しませんが、text-generator ノードの設定にはノード自身が使うのと同じ `tokenizer.json` のパスが書かれているため、スロットはそのファイルを直接読み込みます。`usage` はテキストスロットと同じ基準になり、`tokenizers` 未導入時に空白区切りへ退避するのも同じです。違いは2点残ります。**画像のトークンは数えません**(画像はホスト側でテキストになりません — image-encoder ノードが埋め込みを直接パイプラインへ流すため — なので `prompt_tokens` はプロンプトのテキスト分だけです)。またVLMスロットではコンテキスト超過チェックが走りません。生成量はスロット自身の `max_tokens` で抑えます([VLM(マルチモーダル)対応](#vlmマルチモーダル対応)参照)。

したがって `tokenizers` が「任意」なのは**サーバが起動はする**という意味においてだけです。プロンプトがすべて空白区切りのラテン文字だと確信できる場合を除き、インストールしてください。未インストール時は起動時に警告が出ます。また、パッケージが入っていても **`genie_config.json` が指すトークナイザファイルを読めなかった場合は同じフォールバックに落ちる**ため、思い込みで判断せず起動ログに `HF tokenizer loaded:` が出ているかを確認してください。

## Logprobs

Genie SDKは`GenieDialog`経由でlogitsを公開しませんが、SDKの**カスタムサンプラー**フック(`GenieSampler_registerUserDataCallback` + サンプラー設定`{"type": "custom"}`)が、生成1ステップごとにデクォンタイズ済みfloat32のlogitsベクトル全体をサーバに渡し、出力トークンの選択も委ねます。logprobsはこの仕組みで実装されています(`genie_server/logprobs.py`)。

**生成トークンのlogprobs**(常時利用可): `/v1/completions`の`logprobs`(int)、`/v1/chat/completions`の`logprobs`/`top_logprobs`(bool/int)で、生成各トークンのlogprobと上位N候補を記録します。このリクエストではサンプリングがサーバ側に移ります(同じlogitsに対するgreedy/temperature/top-k/top-p。`temperature=0`はSDKのgreedyと完全一致)。リクエスト終了時にモデル既定値のbasicサンプラーへ復元されます。オーバーヘッドはトークンあたりvocab全体のlog-softmax1回(1〜2ms)で、NPUデコードの数十msに対して数% — logprobsを要求しないリクエストは完全にゼロです。`numpy`とモデルトークナイザが必要。`stream: true`との併用、VLMスロットは非対応(またgrammar制約モデルではマスク後のlogitsに対する値になる点に注意)。

**プロンプトスコアリング**(`echo: true` + `logprobs` — lm_evalのloglikelihoodタスクが送る形状): プロンプトの先頭1トークンのみをprefillし、以降の各プロンプトトークンをデコードループで**teacher forcing**して、各位置の P(token_i | tokens_<i) を記録します — 正確なloglikelihoodと`is_greedy`が得られ、`token_logprobs[0] = null`(先頭トークンの確率は定義不能。OpenAIの`echo`と同じ)。トークンID形式のプロンプト(lm_evalが`tokenizer_backend=huggingface`で送る形式)はID単位で正確に整合します。**各リクエストはプロンプト全体をデコード速度で処理する**(20 tok/sで500トークン文書 ≈ 25秒)ため、以下のゲートがあります:

- 既定で無効。`POST /v1/server/prompt_logprobs {"enabled": true}`(または env_config.json の `PROMPT_LOGPROBS: true`)で有効化、`GET /v1/server/prompt_logprobs`で確認
- `PROMPT_LOGPROBS_MAX_TOKENS`(既定4096)を超えるプロンプトは拒否
- ウォッチドッグはプロンプト長に応じて自動延長。`GET /v1/server/status`のphaseに`scoring prompt`と進捗が出る
- `max_tokens`は0・1・未指定のいずれか。0はプロンプトのスコアのみ、**1はlm_evalの
  loglikelihoodの形**で、実際に生成した1トークンを末尾に付ける(lm_eval側は
  `token_logprobs[ctxlen:-1]`でそれを切り落とす)。2以上は400。

実行スクリプト・lm_evalのインストール手順・実測の所要時間・fp32モデルとの比較方法は
[examples/lm_eval](../examples/lm_eval/README.ja.md) を参照。

注意: 強制トークンがEOSに一致するとその時点でスコアリングが終了します(稀)。プロンプトスコアリングはbasic系のdialog設定が対象です(spec-dec/lookahead系は対象外)。返る数値をGPUリファレンスとどう見比べるかは[スコアリング値の読み方](#スコアリング値の読み方)を参照。

### スコアリング値の読み方

スコアリング経路自体は SA8255P(`qwen3_0_6b`、QAIRT 2.49)で HF transformers と
突き合わせて検証済み — トークナイズは完全一致、teacher forcing の prefix に
1トークンのズレは無く、`temperature` 0 / 1 / 2 や `top_p` を変えても**ビット一致**
(= サンプリング分布ではなく**モデルの分布**を報告している)。

**しかし値そのものは fp32 リファレンスと一致せず、その差は小さくない。**
同ボードで `Qwen/Qwen3-0.6B`(fp32)と比較した実測:

| | |
|---|---|
| per-token logprobs の相関 | 0.84 |
| 平均絶対差 | **1.06 nats**(67トークン位置) |
| 最大絶対差 | 6.76 nats |
| 0.5 nats 以内に収まる割合 | 51% |
| **top-1 次トークンの一致率** | **64%** |

**最後の行が本質**: デプロイされているのは **w4a16** エクスポートであり、
約3分の1の位置で fp32 の元モデルと**最尤トークンすら一致しない**。
logprobs は**量子化されたモデルの忠実な読み出し**であって、
元モデルの読み出しにはなり得ない。

**数値の使い方:**

- **同じボード同士で比較する。** 量子化/エクスポートの変更、KVキャッシュ設定、
  プロンプト整形などの A/B は同一ターゲット上なら有効。
- **ボードのスコアを公開されている fp32 のリーダーボード値と直接比較しない。**
  数ポイントの差はサーバについて何も語らない。
- **`acc_norm` より `acc` を優先する。** hellaswag 8問のサンプルでは、
  合計 loglikelihood は fp32 HF と **8/8** で同じ選択肢を選んだのに対し、
  長さ正規化版は 2/8 でズレた(トークン数で割ると短い continuation では
  per-token の差が増幅される)。どちらかを報告するなら両方報告し、
  **`acc_norm` の方がノイジー**だと扱うこと。
- **ランキングは生き残るが、マージンは生き残らない。** 多肢選択のランキングは
  このサンプルでは保たれたが、候補間の差が1 nat 未満で決まるタスクは
  量子化ノイズに支配される。
- **量子化モデルの方が高いスコアを出すことも普通にある。** 同じサンプルで
  ボードの `acc_norm` は 2/8、HF は 1/8 だった。**これはノイズであって改善ではない。**
  小さな勝ちを実質的な差と読まないこと。

**この検証で確立できなかったこと**: 残差が「全て量子化由来」であること。
証明には同じエクスポートグラフの fp32 実行が必要だがツールチェインが提供していない。
状況証拠(差にシフト・符号・スケールといったサーバ側を示唆する構造が無い)は
整合的だが、証明ではない。

## モデル/LoRAの切り替え

典型的な運用シーケンス(2スロット構成、`chat`側だけ入れ替える例):

```bash
# 1. 現在の状態を確認(全スロット)
curl $base_url/v1/server/status

# 2. 対象スロットの推論が終わるまで待つ(任意、/v1/models/switch自体もそのスロットをブロックするので必須ではない)
curl "$base_url/v1/server/idle?slot=chat"

# 3. chatスロットのモデルを切り替え(tool_callは無停止で稼働継続)
curl -X POST $base_url/v1/models/switch -d '{"slot": "chat", "model_dir": "llama3-8b-htp"}'

# 4. そのスロットにLoRAを適用
curl -X POST $base_url/v1/lora/apply -d '{"model": "llama3-8b-htp", "engine": "primary", "lora_adapter_name": "finetune-v2"}'

# 5. 適用確認
curl "$base_url/v1/lora/current?model=llama3-8b-htp"
```

いずれの操作も対象スロット自身のロックを取得するため、そのスロットへの推論リクエストと安全に直列化されつつ、**他スロットの推論には一切影響しません**。切り替え後、そのスロットの `chat_template`・`active_model_id`・prefixキャッシュのnamespaceは自動的に新モデルのものへ切り替わります。

## Open WebUI

Open WebUI は**サーバ側の設定変更なし**で本サーバに繋がりますが、
**何を送ってくるかは Open WebUI のリリースごとに変わります**。その変化のひとつが、
コンテキストの小さいモデルで**応答を空にする**ことがあります。以下のバージョンは
**実測した点であって互換性マトリクスではありません** — 試していないリリースでは、
同じ対処が要るかもしれませんし、別の対処が要るかもしれませんし、何も要らないかもしれません。

| バージョン | 時期 | 結果 |
|---|---|---|
| v0.6.18 | 2026-08-22 | **そのまま動作**。モデル一覧・チャット・ストリーミングとも問題なし。セッション中のボード側 **4xx/5xx はゼロ** |
| 0.11.0 | 2026-08-22 | **組み込みツールのチェックを外せば動作**(下記) |

```bash
docker run -d --name open-webui -p 3001:8080 \
  -e WEBUI_AUTH=False \
  -e WEBUI_SECRET_KEY=<任意の固定文字列> \
  -e OPENAI_API_BASE_URL=http://<ボード>:8080/v1 \
  -e OPENAI_API_KEY=dummy \
  -e ENABLE_OLLAMA_API=false \
  -e ENABLE_EVALUATION_ARENA_MODELS=false \
  -v open-webui:/app/backend/data \
  ghcr.io/open-webui/open-webui:<実際に動かすタグ>
```

### 応答が空になるとき、まず組み込みツールを疑う

Open WebUI には組み込みツール(knowledge base、memories、notes、tasks、automations、
calendar)があり、**バージョンによっては、そのすべてを毎回のチャットリクエストに
`tools` として送ります**。0.11.0 ではこれをプロンプトに展開すると **約5,800トークン**になり、
Qwen3 エクスポートの 4,096トークンのコンテキストを超えるため、生成の余地が無くなって
**応答が空**になりました。

**Open WebUI のツールメニューで組み込みツールのチェックを外せば直ります** — 0.11.0 では
これで動作しました。より新しいリリースでも、既定で大きなものを送ってくるなら**まずここを
確認**してください。送ってくるものが別のものであっても、**問題になるのは名前ではなく大きさ**です。
他の逃げ道は、コンテキストの大きいモデルを使うか、これらを送らないバージョンを使うことです
(v0.6.18 は送りません)。

なお**サーバはこれを空の `200` で誤魔化しません**。入りきらないプロンプトには
**OpenAI準拠の `400 context_length_exceeded`**(両方のトークン数を明示)を返すので、
「クライアントが送りすぎた」のか「モデルが何も言わなかった」のかを区別できます:

```json
{"error": {"message": "This model's maximum context length is 4096 tokens. However, your messages resulted in 5790 tokens. …",
           "type": "invalid_request_error", "param": "messages", "code": "context_length_exceeded"}}
```

### バージョンによって変わりうる、もう2点

どちらも 0.11.0 の挙動で、v0.6.18 には無かったものです。**次のリリースでもまた変わりうる**
という点が重要です。

- **送信前にモデル一覧を検証することがある。** 0.11.0 は `/v1/models` のエントリに
  legacy の `root` / `parent` / `permission` が無いモデルへは**送信を拒否します** —
  モデル選択には出るのに何も起きません(現在は返すよう修正済み)。**別のフィールドを
  要求するバージョン**があっても外からは同じに見えるので、「選べるのに送られない」ときは
  `GET /v1/models` の応答と、そのバージョンが期待するものを突き合わせてください。
- **ストリーム応答がHTTPレスポンスで返らないことがある。** 0.11.0 は自身のwebsocket
  チャネル経由で描画します。サーバからは見えませんが、**APIではなくUIをデバッグするときに
  どこを見るか**が変わります。

### 最初から正しくしておきたい設定

以下4点ははまりどころで、**どれもバージョン依存ではありません**:

| 設定 | 理由 |
|---|---|
| `WEBUI_SECRET_KEY` | 未設定だと**コンテナ起動のたびにJWT署名鍵が再生成**され、既存セッションが全て壊れる。症状はサインイン/サインアウトのループと、ブラウザコンソールの `No token found in localStorage` |
| `OPENAI_API_BASE_URL` | **初回起動時にDBへ書き込まれるだけ**。後から環境変数を変えても無視され、DBの値が優先される。管理画面 → Connections で直すか、ボリュームを作り直す |
| `ENABLE_EVALUATION_ARENA_MODELS=false` | 無効にしないとモデル一覧に `arena-model` が現れ、arena用モデル未設定のまま選ぶとフロントが無言で失敗する |
| タスク用モデル | タイトル/タグ/フォローアップ生成は「タスク用モデル」で走るが既定が空文字で、`Model '' was not found` になる。管理画面 → Interface で実モデルを指定するか、機能自体をオフにする |

**遅いターゲットでは裏タスクを切ること。** タイトル・タグ・フォローアップ生成はそれぞれ
追加のチャット補完を発行し、スロットは1リクエストずつしか処理しません。4B(約11 tok/s)では
1メッセージあたり数秒の追加コストになります。

容量設計のために、サーバから見える実際の挙動: Open WebUI は **`GET /v1/models` を高頻度で
ポーリング**し(検証セッションではチャット34件に対し66回。メモリ上の応答なので軽量)、
毎ターン会話履歴を丸ごと送るため **TTFTが履歴とともに増えます**(3ターンで
184ms → 358ms → 535ms。AR-128バッチ境界を越えるたびに段階的に増加)。
常にシステムメッセージを含むので [prefix cache](#prefix-kvキャッシュ) の対象です —
長いシステムプロンプトを使う構成なら温めておくとよいでしょう。

## lm_eval 連携

```bash
# 生成ベースのタスク(gsm8k, humaneval, *_generative系 …)
lm_eval --model local-completions \
  --model_args model=genie-local,base_url=http://192.168.1.2:8080/v1,\
tokenizer_backend=huggingface,tokenizer=<hf_model>,max_tokens=512,num_concurrent=1 \
  --tasks gsm8k --batch_size 1

# チャットタスク
lm_eval --model local-chat-completions \
  --model_args model=genie-local,base_url=http://192.168.1.2:8080/v1,\
tokenizer_backend=huggingface,tokenizer=<hf_model>,max_tokens=512,num_concurrent=1 \
  --tasks mmlu_generative --apply_chat_template --batch_size 1
```

- **loglikelihoodベースのタスク(hellaswag, arc_easy, 素のmmlu等)はプロンプトスコアリングで実行可能**です。事前に有効化が必要です(`POST /v1/server/prompt_logprobs {"enabled": true}` — [Logprobs](#logprobs)参照)。各文書はデコード速度でスコアリングされる(1リクエスト数秒〜)ため、現実的な実行時間には`--limit`や短コンテキストのタスクを推奨。生成ベースのタスクが引き続き高速パスです。スコアリング無効時の`echo`+`logprobs`要求には、有効化スイッチを明示した`400`が返ります。
- `tokenizer_backend=huggingface` を指定すると`lm_eval`はトークンID形式のプロンプトを送ります。サーバはそれをスロット自身のトークナイザでデコードするため、`genie_config.json`の`dialog.tokenizer.path`と`lm_eval`に渡すHFトークナイザを一致させてください。

- `num_concurrent=1` を推奨。単一スロット構成ではサーバ全体が直列処理のため並列度を上げてもスループットは増えません。2スロット構成で**両スロットを同時にベンチマークしたい場合**は、片方を`model=genie-local`(プライマリ)、もう片方を明示的な`model=<2つ目のactive_model_id>`に固定した2つの`lm_eval`プロセスを並行実行してください(1プロセス内の`num_concurrent>1`はスロットを跨いだ負荷分散をしません)。

## BFCL(function calling ベンチマーク)

[BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html) の OSS 向けハンドラは
`/v1/completions` を話すため、本サーバに対してそのまま実行できます。実行スクリプト・
インストール手順・カテゴリ別の所要時間は [examples/bfcl](../examples/bfcl) を参照。

**BFCL は本サーバのチャットテンプレートとツールパースをバイパスします。**
各ハンドラがプロンプトを自前で組み立て(HF tokenizer のチャットテンプレートから
Hermes 形式、gemma4 ハンドラなら gemma4 のマーカー)、`/v1/completions` に
生テキストを送り、応答から呼び出しを自前でパースします。
`/v1/chat/completions`・`tools`・`tool_choice`・`TOOL_CALL_RECOVERY` は一切関与しません。
リーダーボードとしては正しい設計ですが、**`<tool_call>` マーカーが不安定なモデルは
実力より大幅に低い点数になり、本サーバの回収機能では救えません** — マーカーが化けた
正しい呼び出しは `Wrong number of functions.` と採点されます。そうしたモデルのスコアは
下界であって、公開リーダーボードと比較する数字ではありません。見分け方は
`examples/bfcl/README.ja.md` に記載しています。

## パフォーマンスポリシー

`POST /v1/server/performance_policy` は `Genie_PerformancePolicy_t`(`burst` から `extreme_power_saver` までの9段階)をSDKに渡します。本来はHTPバックエンドの電力/クロック制御に届き、速度と消費電力を引き換えにするためのものです。

**デバイスがこれに従うかはターゲット依存であり、従うと決めてかからないでください。** ハイパーバイザのゲストとして動作しているSA8255Pでの実測では、**9種すべてが同じ数値**になりました。9ポリシー × 4ラウンドを交互に巡回した36本(4Bモデル、プロンプト378トークン、ストリーミング計測)で、TTFTの中央値は 561.8〜566.2 ms、デコードは 10.79〜10.83 tok/s — それぞれ 0.8% と 0.4% の幅しかなく、`burst` と `extreme_power_saver` が区別できません。**同一ポリシー内のばらつきの方が、ポリシー間の差より大きい**状態です。モデルバンドルのHTPバックエンド拡張設定にプロファイルを焼き込んで再起動しても変わらなかったので、ランタイム呼び出しが捨てられているのではなく、デバイスがプロファイルを見ていないということになります。

このエンドポイントを使う側にとっての帰結は2つです:

- **GETは証拠になりません。** 返るのはSDKが保存した値であってデバイスから読んだ値ではないため、往復が完璧に通っていても何も起きていない場合があります。効果の有無を知る手段は実測だけです。
- **依存する前に測ってください。** ポリシーが効くターゲットなら、ベンチマーク前に `burst` に固定する価値があります。効かないターゲットでは、固定しても害はありませんが何も得られません。

なお上記の実測は**速度だけ**で、消費電力は測っていません。レイテンシもスループットも動かないポリシーが電力を下げているとは考えにくいものの、それは推測であって計測結果ではありません。省電力側のトレードオフが必要な場合は、電力を直接測ってください。

APIを残してあるのは、コストが無く、答えがターゲットごとに異なるからです。新しいハードウェアでこのサーバを立ち上げるときは、`burst` と `extreme_power_saver` でそれぞれ数回の生成を計測してから、これが本当に使えるつまみなのかを判断してください。

## ベンチマーク運用

ベンチマーク実行時に再現性のある数値を取りたい場合の推奨手順:

1. `POST /v1/server/performance_policy {"model": "...", "policy": "burst"}` で対象スロットの性能ポリシーを固定。ポリシーが効くターゲットではばらつきの要因を1つ減らせますし、効かないターゲットでも害はありません([パフォーマンスポリシー](#パフォーマンスポリシー)参照)。
2. `GET /v1/server/idle?slot=<name>` でそのスロットが空くのを待ってから計測開始。
3. TTFT(Time To First Token)はサーバログに `TTFT [<request_id>] slot=<name> cache=<HIT|MISS|NONE> <ms>ms` として自動出力されます(共通の生成エンジンが出力 — `/v1/completions`・`/v1/chat/completions`共通)。
4. `GET /v1/server/status` の `slots[].context_occupancy` でスロットごとのKVキャッシュ占有量を、推論をブロックせずフェーズ間で監視できます。
5. マルチターン/長文脈ベンチマークでは `POST /v1/prefix/warmup` でシステムプロンプトを事前キャッシュしておくと、初回リクエストのprefill時間を除外して計測できます。
6. 2スロットを同時にベンチマークする場合は、各スロットで独立にこの手順を回してください(お互いをブロックしません)。
7. ベンチマーク終了後は `POST /v1/server/performance_policy {"policy": "balanced"}`(またはターゲットの既定値)に戻すことを推奨します。

## トラブルシューティング

| 症状 | 確認ポイント |
|---|---|
| 起動時に `sys.exit(1)` で即終了 | `env_config.json` の存在、各スロットの`model_root`配下の`genie_config.json`と参照ファイル(tokenizer/extensions/ctx-bins)の実在を確認。ログの `Required asset not found` / `GenieDialogConfig_createFromJson failed` / `Failed to load model for slot '<name>'` を参照。 |
| `libGenie.so` のロードに失敗 | `QAIRT_SDK_ROOT`・`ADSP_LIBRARY_PATH` の設定、`lib/aarch64-oe-linux-gcc11.2/libGenie.so` の実在を確認。ターゲットプラットフォームが異なる場合は該当パスを修正。 |
| 応答が期待するテンプレートと異なる | `/v1/server/status` の該当スロットの`active_model`(または起動ログの `Slot '<name>' ready: model=... template=...`)を確認。`CHAT_TEMPLATE` を明示指定するか、モデルディレクトリ名にヒントとなる文字列(`llama3`/`llama2`/`mistral`)を含める。 |
| `finish_reason` が期待とズレる | `"length"` は `max_tokens` 到達時(SDKは通常のstopとして報告するためサーバ側でカウント判定)または `GENIE_STATUS_WARNING_CONTEXT_EXCEEDED` の場合。クライアント切断時のabortは `"stop"`(既定値)のまま返る仕様。 |
| 2つ目のスロットにリクエストが届かない | リクエストの`model`フィールドが、対象スロットの`active_model_id`(=モデルディレクトリ名)と完全一致しているか`GET /v1/models`または`GET /v1/server/status`で確認。一致しない文字列は常にプライマリスロット(`slots[0]`)に落ちる仕様。 |
| モデル切り替え後もLoRAが残っている | `/v1/models/switch` 成功時は対象スロットの `active_lora_adapter` を自動的に `""` にリセットしますが、SDK内部状態と食い違う場合は `/v1/lora/current?model=...` で実際の値を確認してください。 |
| prefix warmupが `422` | 対象スロットのモデルのテンプレートがllama2/mistralの場合、systemプロンプトは`[INST]`に融合されるため分割・キャッシュ不可(仕様)。 |
| `device_id`を指定したのにNSPが固定されていない | 起動ログに `device_id=... requested but ... has no dialog.engine.backend.extensions file to patch — NSP pinning skipped` の警告が出ていないか確認。モデルの`genie_config.json`にHTPバックエンド拡張設定ファイルへの参照が無いと固定できません。 |
| あるスロットが突然、全リクエストで `GenieDialog_query failed [...]: -1` / `batch dispatch failed` を返すようになる | スロットに楔が入っています。素のQAIRT 2.49.40.260810 の `libGenie.so` と、複数のコンテキスト長でエクスポートされたモデルの組み合わせです。原因となったリクエスト自身は成功して正常に返っており、失敗し始めるのはその次からです。`GenieDialog_reset()` では復旧しません。**復旧方法**: そのスロットを `POST /v1/models/switch {"slot": "<名前>", "model_dir": "<同じモデル>"}` で再ロードします。**回避方法と詳しい説明**: [QAIRT バージョン別の問題点](./QAIRT_VERSIONS.ja.md#d1--素のライブラリはスロットを壊す)を参照。 |

## 制約事項

- **本サーバは素のライブラリでのスロット恒久故障を防ぎません**。検知も自動復旧もせず、モデルが再ロードされるまでそのスロットは失敗し続けます。回避はサーバの設定ではなくデプロイ側の選択です — [QAIRT バージョン別の問題点](./QAIRT_VERSIONS.ja.md)を参照。
- 1スロット = 1 `GenieDialog` ハンドルの直列処理。同時に処理できる推論は「スロット数」件まで(単一スロット構成では1件のみ)。
- `n > 1`(1リクエストで複数補完)は非対応。
- `logprobs` は `numpy` + モデルトークナイザが必要で、非ストリーミングのみ。プロンプトスコアリング(`echo`+`logprobs`、lm_eval loglikelihood)はプロンプト全体をデコード速度で処理するため既定で無効([Logprobs](#logprobs)参照)。
- 実行時の `presence_penalty`/`frequency_penalty` は受理するが無視される: SDKのランタイムサンプラ更新経路(`GenieSampler_applyConfig`)は `seed`/`temp`/`top-k`/`top-p` しか適用しない。
- Llama2/Mistralテンプレートはprefix KVキャッシュ非対応。
- `--workers` を1より大きくして起動しないこと(各スロットのグローバルなNPUハンドル状態が壊れます)。
- `POST /v1/models/switch` は既定で旧モデルを解放してから新モデルをロードするため、ロードに失敗するとそのスロットは完全に未ロード状態になることがあり、以降そのスロットに触れる全エンドポイントが次のswitch成功まで`503`を返します。`"unload_first": false` は新旧を同時にHTPデバイスへ載せることで旧モデルをフォールバックとして残せますが、**SA8255Pボードではこの同時常駐は当てになりません** — 36回のスワップを実測した結果、成否はどのモデルの組み合わせかでは決まらず(同じ組み合わせがあるときは6/6、別のときは0/8)、デバイスのメモリに余裕があり、かつ自分たちのスワップをそこでテスト済みの場合にのみ使う価値があります。エンドポイント自身の説明を参照。
- 2つのスロットが同じ`active_model_id`(モデルディレクトリ名)を持つ場合、`model`フィールドによる自動ルーティングは`slots`配列内で後にあるスロットを優先します。`/v1/completions`/`/v1/chat/completions`のbodyに明示的に`"slot": "<名前>"`を指定すればそのスロットを直接指定できます(`model`によるルーティングより優先)。他にもスロット名を直接使うAPI(`/v1/models/switch`の`slot`、`/v1/server/idle`の`?slot=`)があります。
- **素の 2.49.x ライブラリでは、`dialog.type` が `ssd-q1`(投機デコード)のバンドルにパッチ版が要ります。** 本サーバは毎クエリ前にリセットしますが、素の 2.49 ではこの種のダイアログがそれに耐えないためです。同じ理由で LoRA も使えません。これは投機デコードバンドル一般の制約ではなく **2.49 の回帰**で、2.48.40.260702 では正しく動きますし、以後の SDK で直る可能性もあります。症状・原因・手元の SDK のソースで1分で確かめる方法・パッチを当てられない場合の対処は [D5](./QAIRT_VERSIONS.ja.md#d5--リセットが投機デコードのダイアログを壊す) にあります。
- Grammar制約([該当セクション](#grammar制約デコーディング))はモデル/スロット単位で固定であり、`response_format`のようなリクエスト単位の切り替えには対応していません(Genie SDKの公開APIに実行時変更手段が無いため)。
- VLM([該当セクション](#vlmマルチモーダル対応))は単発リクエストのみ(会話履歴なし)。リクエスト側の`max_tokens`/`stop`は無視され、生成長は代わりにスロット単位の`VLM_SLOTS[].max_tokens`で制限されます。クライアントが切断しても実行は止まりません — `GenieNode`/`GeniePipeline`にabort呼び出しが無いため、応答が終わるまでスロットは占有され、次のリクエストは待たされます。ストリーミングは動作し、非ストリーミングと同じテキストを返します。LoRA・Prefix KVキャッシュ・grammar制約・`/v1/models/switch`はVLMスロットには非対応です。
