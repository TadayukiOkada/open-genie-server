open-genie-server は `libGenie.so` の薄いクライアントです。本サーバ自身のバグでない
障害のほとんどは、**どの QAIRT SDK ビルドで動かしているか**の性質です。
本ページは「どのビルドが何を抱えているか」を記録する唯一の場所です。

「サーバの使い方」に集中させるため)。SDK ビルドを選ぶとき、モデルのエクスポート形式を
決めるときは、まずこのページを読んでください。

## 根拠欄の読み方

- **実測** — 実機で再現した。単体の再現プログラム、または本サーバ経由。
- **ソース同一** — SDK は Genie ライブラリの完全なビルド可能リファレンスソースを
  `examples/Genie/Genie/` に同梱している。ある欠陥を実装しているファイルが2つのビルドで
  バイト単位で同一なら、その欠陥は両方に存在する。D1・D2 の該当ファイルは
  `qualla/dialog.cpp` と `qualla/engines/qnn-htp/KVCache/kvmanager.{cpp,hpp}`、
  D5 は `qualla/dialogs/ssd-q1.cpp` で、いずれも
  2.49.40.260810 と 2.49.1.260821 の間で同一である
  (`ssd-q1.cpp` は 2.48.40.260702 とは**異なり**、その差分がまさに D5 である —
  両ビルドの `SelfSpecDecDialog::reset()` はバイト単位で同一で、
  2.49 で増えたのは `completeInit()` 側のスロット関連呼び出しであり、
  `reset()` がそれに追随していない)。
  **これはソース上の論証であって実機実行ではない** — D1・D2 の再現プログラムを
  2.49.1 で走らせ直してはいない。**2.50.0.260828 はこの扱いではない** —
  D1・D2・D4・D5 は実機で走らせ直した。ソース論拠なのは D3 だけで、
  `qualla/grammar.hpp` が同一であり、宣言しているバックエンドを定義した
  ファイルはこのビルドにも同梱されていない。**2.51.0.260929**: D1・D2・D3・D4・D6 は
  実機で確かめた(D1・D2 は複数コンテキスト長と単一コンテキスト長の両方のバンドルで)。
  D5 はソース論拠 — ボードに `ssd-q1` のバンドルが無かった。**2.52.0.261104**: D4・D6 は
  実機で確かめ、D3 はソース論拠。D1・D2・D5 の再現プログラムは走らせ直しておらず、
  これらの行は 2.51.0 の結果を引き継いでいる。**D7** は素の 2.52.0 と、本プロジェクトの修正を
  入れてリビルドした 2.51.0 で実測した。関係するコード(`qualla/dialog.cpp` の停止系列の削除と
  `SlidingWindow::processReduce`)は素の 2.51.0 でも同じ。
- **再現せず** — 再現プログラムを走らせたが発火しなかった。「無い」より弱い主張で、
  「その手順ではそのビルドは安全」であって「どんな手順でも安全」ではない。
- **修正済み** — 前のビルドにはあり、原因のコードが直された。「(実測)」は実機で再現
  プログラムが発火しなくなったこと、「(ソース上の論証)」はソースを読んだだけであることを示す。
- **無し(ソース上の論証)** — その欠陥を生むコードがそのビルドに存在しない。
  これも実機実行ではなくソースからの論証であり、**探していない欠陥については何も言わない**。
- **未検証** — どちらの主張もしていない。

**D1・D2・D5 の出どころ**。2.49 は継続バッチングスケジューラ
(`qualla/engines/inference-scheduler.cpp`。**2.48 には存在しないファイル**)を導入し、
それに合わせて dialog のリセット経路を組み直した。3つの欠陥はいずれもこの組み直しの中にある —
リセット経路が「キャッシュを丸ごと巻き戻していた呼び出し」を通らなくなり、
代わりに入ったものが全部は巻き戻さない。2.48 で D1・D2 が再現しないのはこのためであり、
**D5 が 2.48 では起こり得ない**のも同じ理由である
(2.48 には D5 が問題にしているスロット関連の呼び出しがそもそも無く、
コンストラクタとリセット経路が互いに同じことをしている)。

## D1 — 素のライブラリはスロットを壊す

> [!WARNING]
> 素の 2.49.x ライブラリでは、**プロンプト + 生成**のトークン数がキャッシュ予算を
> 超えたリクエストが、そのスロットを恒久的に壊します。超えたリクエスト自身は正常に返り、
> **その後の**あらゆるリクエスト(ごく単純なものも含む)が、その `GenieDialog` が
> 存在する限り `GenieDialog_query failed [...]: -1`(ログには `batch dispatch failed`)で
> 失敗し続けます。本サーバが毎リクエスト前に呼んでいる `GenieDialog_reset()` では
> 復旧しません。モデルの再ロードだけが復旧手段です。

**予算は `コンテキスト長 − AR_N`**(コンパイル済みの最小コンテキスト長について)。
`AR_N` はどの API にも出てきません。バンドルのグラフ名にあります:

```sh
grep -aoE 'ar[0-9]+_cl[0-9]+' part1_of_N.bin | sort -u
#   ar128_cl4096
#   ar1_cl4096      -> AR_N = 128, CL = 4096, 予算 = 3968
```

**複数コンテキスト長のバンドルは早い段階で踏みます。** この種のバンドルは複数の
コンテキスト長で同時にコンパイルされており(Qwen3 w4a16 バンドルは
`context_lengths: [512, 1024, 4096]`)、SDK はトークン数の増加に応じてバリアント間を
移動します。**上がる**のは問題ありません。壊れるのは**下りてくる**ときです。
よって境界は最初の切り替えが起きる場所 = `512 − 128 = 384 トークン`。
この数字は設定のどこにも現れず、モデルの能力の上限でもありません。

`qwen3_0_6b` での実測(`prompt_tokens + completion_tokens`):

| 合計 | 結果 |
|---|---|
| 384 | ok |
| 385 | スロット破壊 |

境界をプロンプト処理中に跨ぐか生成中に跨ぐかは**関係ありません**:
プロンプト380 + 生成4 は無事、プロンプト168 + 生成256 は駄目です。

### 単一コンテキスト長は予算を引き上げるが欠陥を消しはしない

> [!WARNING]
> **以前は逆に書かれていました。同じ誤りを繰り返しやすいので経緯を残します。**
> 当時の測定は `max_tokens` を小さくして**プロンプト長**で二分探索したため、
> プレフィル経路しか動かしていませんでした。そしてプレフィルの超過は、
> **唯一まともに振る舞う経路**です。デコード経路は一度も試していませんでした。

単一コンテキスト長が変えるのは**予算の位置**であって、跨げるかどうかではありません。
開始点となる小さいバリアントが無いので、予算は唯一のバリアントについて
`コンテキスト長 − AR_N` — `[4096]` / AR-128 のバンドルなら 384 ではなく **3968** です。
偶然到達するのは格段に難しくなりますが、到達はします。

素のライブラリ・`[4096]` バンドル1本で、2つの経路を分けて測った結果:

| 予算を超えるもの | 合計トークン | 結果 |
|---|---|---|
| なし(対照) | 3576 | 無事 |
| **生成** | 4048 | **破壊** — しかもリクエストは 200・`finish_reason: "length"`・**警告なし**で返る |
| **生成** | 4069 | **破壊** |
| プロンプト単独 | 4083 | 無事 — `GENIE_STATUS_WARNING_CONTEXT_EXCEEDED`、生成ゼロ、dialog は使用可能なまま |

つまり、**プロンプト単独で溢れる分にはきれいに拒否されます**。プロンプトは収まるが
`max_tokens` によって合計が予算を越えるリクエストがスロットを壊し、しかも
**そのリクエストは完全に成功したように見えます**。

罠の実際の形: `[4096]` バンドルに対する「プロンプト3698トークン + `max_tokens: 350`」は
ごく普通の要約リクエストで、`prompt_tokens <= context.size` という当たり前のチェックを
通過し、スロットを殺します。

> [!WARNING]
> **素の 2.49.x と 2.50.x では、構成だけで安全になる選択肢はありません。**
> 単一コンテキスト長でエクスポートしても、`prompt_tokens + max_tokens` を
> `コンテキスト長 − AR_N` に自分で抑える必要は残ります。
> **open-genie-server はこれを代行しません** — サーバのコンテキストチェックは
> プロンプトしか見ていません。

**原因**。実行中のトークン数が小さいコンテキストバリアントを超えると、SDK は
KV キャッシュを正しく大きい方へ reshape します。しかし**そのキャッシュエントリを
返却することが一度もありません** — キャッシュグループの「有効KVエントリ数」カウンタは
継続バッチング経路で増える一方で、リセット経路にこれを減らすものが無いのです。
次のリクエストが再び小さいプレフィルバリアントを要求すると、その切り替えが
予算超過として拒否され、**その拒否の戻り値が捨てられている**ために、エンジンは
食い違ったグラフテンソルのまま先へ進み、汎用的な `batch dispatch failed` として失敗します。

単体の再現プログラムを添えて Qualcomm へ報告済み。**2.51.0.260929 で直りました**:
素の 2.51.0 では、複数コンテキスト長のバンドルでも単一コンテキスト長のバンドルでも
再現プログラムが発火せず、リセット経路がキャッシュグループを巻き戻すようになっています。

## D2 — リセットが KV 位置アロケータを巻き戻さない

D1 とは別の、2つ目のリセット欠陥。**2.49 の回帰**で、2.48 では再現しません。

症状: 長い生成 → EOS で自然終了する短い生成 → もう一度長い生成、という順で、
**3回目がプレフィル段階で** `GENIE_STATUS_WARNING_CONTEXT_EXCEEDED` で失敗します。
コンテキストは 4096、プロンプトは数百トークン、しかも毎回 dialog をリセットしているのに、です。
スロットは復旧しません。

**原因**。スロットのリセットは KV 位置をフリーリストの**末尾**に積み直しますが、
確保はフリーリストの**先頭**から取り、しかも高水位カーソルが巻き戻りません。
長い実行のあとに短い実行を挟むと、次のリクエストにはゼロからではなく
キャッシュの途中から始まる位置が渡され、エンジンがそのバッチを拒否します。
**同じ長さのリクエストを並べても再現しません** — **長い → 短い → 長い**が必要です。

D1 だけを直してもこれは直りません。症状が D1 の `-1` からこの警告に変わるだけです。

D1 と併せて Qualcomm へ報告済み。**2.51.0.260929 で直りました**(実測):
長い → 短い → 長いの再現プログラムが発火しません。

## D3 — リビルドしたライブラリには grammar が入らない

**これはバージョン固有ではありません。** 当方が見た 2.48.40.260702 から 2.51.0.260929 までの
どのビルドでも同じです。

XGrammar バックエンドは **SDK のソース同梱物に含まれていません**。
`GrammarBackend::create` は `qualla/grammar.hpp` で宣言されているだけで、
同梱されたどのソースファイルにも定義がなく、同梱のビルドファイルに
`ENABLE_GRAMMAR` オプションもありません。したがって `examples/Genie/Genie/` から
ビルドしたものは、`genie_config.json` に `dialog.context.grammar` を持つ dialog の
生成を拒否します:

```
Grammar backend configured but qualla was built without ENABLE_GRAMMAR; rebuild with -DENABLE_GRAMMAR=ON
```

そして `GenieDialog_create` が `-1` を返します。**このメッセージが名指ししているフラグは
同梱のビルドシステムに存在しない**ので、その助言には従えません。

任意のライブラリを判定する方法:

```sh
strings libGenie.so | grep -ci xgrammar
#  96  -> 2.48.x〜2.50.x の stock(grammar 使用可)。2.51.0 の stock は 97
#  1〜2 -> リビルド版(grammar はコンパイルから外れている)
```

2.48.40〜2.50.0 で確認済み: grammar の実装ファイルは無し、ビルドファイルに
`ENABLE_GRAMMAR` も無し、同梱の `.so` はいずれも 96。2.51.0 も同じで、97。

**2.51.0 で入ったリクエスト単位の grammar の API も、リビルド版では使えません。**
`GenieDialog_setGrammar` はエクスポートされていますが、呼ぶと毎回失敗します。
本サーバはモデルのロード時にこれを見分け、そのスロットへの `response_format` /
`structured_outputs` を `400` `grammar_not_supported` で断ります
([MANUAL § grammar制約デコーディング](./MANUAL.ja.md#grammar制約デコーディング))。
リビルドした 2.51.0 のライブラリ 2 本で実測。

**つまり 2.49.x と 2.50.x では、D1/D2 を直すことは無料のアップグレードではなく二者択一です**。
素のライブラリは grammar が使えるがリセット欠陥を抱え、リビルド版は欠陥が直るが
grammar を失います。これらの版では **SDK が用意するものの中に、grammar と「壊れないスロット」を
両立させる組み合わせはありません。** 2.51.0 では素のライブラリが両方を持つので、
D6 のためにリビルドするのでなければ二者択一はなくなりました。
バックエンドをソース同梱物に含めるよう Qualcomm へ要請済み。

**バックエンドは自分で用意できます。** XGrammar はオープンソース(Apache-2.0)です。
宣言だけある `GrammarBackend::create` を上流のライブラリの上に実装し、`ENABLE_GRAMMAR` を
定義してビルドすれば、リビルド版にも grammar が入ります(バンドルの grammar もリクエスト単位の
API も)。当方は 2.51.0 でこれを行い、本サーバを使って実機で確かめました。そのライブラリには
D4 の修正も入れられます。パッチはここでは配布していません。

## D4 — grammar が終端トークンを本文に漏らす

素のライブラリで grammar 制約デコーディングを使うと、3種別(JSON Schema・正規表現・EBNF)
いずれも出力は正しく制約されますが、**応答の末尾にモデルの終端トークンが
そのままテキストとして残ります**(ChatML 系なら `<|im_end|>`)。
サーバ側では除去していません。
[MANUAL § grammar制約デコーディング](./MANUAL.ja.md#grammar制約デコーディング)を参照。

2.49.40.260810・2.50.0.260828・2.51.0.260929 で実測 — 8件の grammar チェックのうち同じ5件が、
3つとも同じように落ちます。2.51.0 では、リクエスト単位の grammar(`response_format`、
`structured_outputs`)も同じトークンを漏らします。他のビルドでは未検証。

原因は SDK の basic dialog の 1 つの分岐です。grammar が出力の終わりを告げると、
終端トークンをテキストとしてトークンのコールバックへ渡しています。この分岐がトークンを
渡さないように直してリビルドしたライブラリでは漏れなくなりました(3種別とも実機で確認)。

## D5 — リセットが投機デコードのダイアログを壊す

`dialog.type` が `ssd-q1`(forecast prefix を使う自己投機デコード)のバンドルにのみ該当します。
該当するバンドルは、設定ファイルの隣に `forecast-prefix/` ディレクトリがあり、
コンテキストバイナリの名前が `..._ar128_ar1_...` ではなく `..._ar64_ar128_...` になっています。

症状: `GenieDialog_reset` の後、**1トークン目だけ正しく、以降が無関係なトークンに崩れます** —
それらしい単語が並ぶのにプロンプトとの関係が無い、という壊れ方です。ステートレスなサーバは
リクエストを独立させるため毎回リセットするので、**実質すべての応答**がこうなります。

**原因**。`SelfSpecDecDialog::completeInit()` はエンジンのスロットを用意し、forecast prefix を
復元し、ダイアログの `_n_past` を設定したうえで、**`initSlotFromRestore()` を呼んでエンジン側の
スロットにもそれを伝えます**。`SelfSpecDecDialog::reset()` は真ん中の2つしか行いません。
その直前に呼ばれる `Dialog::reset()` が**そのスロットの `n_past` を 0 にしている**ため、
ダイアログは「エンジンが知らない prefix を持っている」と思い込み、
1トークン目以降の位置がその長さぶんずれます。

実機で二分探索して特定しました — クエリ前の SDK 呼び出しを1つずつ無効化していくと、
**リセット単独**に絞り込めます。リセットを一切呼ばない SDK 純正の `genie-t2t-run` は、
**同じバンドル・同じ設定で正常**です(確保量も 8 バッファ・188MB と完全に同一)。

**LoRA も道連れになります。** SDK はアダプタ切替後のリセットを要求するので、`ssd-q1` バンドルで
アダプタを適用すると、リセット有りならダイアログが壊れ、無しならアダプタが効きません。

**ソースパッチで修正できます** — D1・D2 を直すのと同じリビルドです。`reset()` を
`completeInit()` と同じ形にするだけで、**1関数・14行、ABI 変更なし**
(エクスポートシンボル118個と `NEEDED` は同一)。実機で確認済み: `ssd-q1` のまま正しく生成し、
**リセットをまたいで応答が独立**し、**LoRA も使えるようになり**、投機デコードの利得も出ます
(同じプロンプト・同じバンドルを `basic` にした場合の **3.57 tok/s に対し 4.42 tok/s**)。
非投機の経路に回帰はありません。

**パッチを当てない場合**は、バンドルの `dialog.type` を `basic` に書き換えて `ssd-q1` ブロックを
削ってください。同じコンテキストバイナリがそのままロードでき、正しく生成します。
失うのは投機デコードによる高速化であって、モデルではありません。

**どのバージョンの話か。** これは **2.49 の欠陥**で、手元の 2.49 すべてに存在します
(2.49.40.260810 で実測、2.49.1.260821 は `ssd-q1.cpp` がバイト同一)。
**2.48.40.260702 では起こり得ません** — ここで問題にしているスロット関連の呼び出しは
2.49 のスケジューラとともに入ったもので、2.48 ではコンストラクタと `reset()` が
もともと同じことをしているためです。**2.50.0.260828 では直っていません** —
`ssd-q1.cpp` は 2.49.40.260810 とバイト同一で、再現プログラムもそのまま発火します。
**2.51.0.260929 ではソース上で直っています**: `reset()` がスロットを準備して
`initSlotFromRestore()` を呼ぶようになりました(当方のパッチと同じ変更)。
ボードに `ssd-q1` のバンドルが無く、実機では走らせていません。
確認は SDK 同梱のソースで1分で済みます:
`examples/Genie/Genie/src/qualla/dialogs/ssd-q1.cpp` を開き、
`SelfSpecDecDialog::reset()` と `SelfSpecDecDialog::completeInit()` を見比べてください。
**`completeInit()` が prefix 復元の前後で `prepareSlot()` と `initSlotFromRestore()` を
呼んでいるのに `reset()` が呼んでいなければ、この欠陥があります。**
両方が呼んでいる、あるいは両方とも呼んでいないなら、ありません。

## D6 — 保存と復元がスライディングウィンドウのキャッシュグループを壊す

スライディングウィンドウのキャッシュグループを持つバンドル(Gemma 4 にある)と、それに
`GenieDialog_save` / `GenieDialog_restore` を使うもの — 本サーバでは
[prefix KV キャッシュ](./MANUAL.ja.md#prefix-kvキャッシュ) — が対象です。グループの予算
(測った Gemma 4 E2B のバンドルで約 640 トークン)より長い prefix を復元すると出力が変わり、
もっと長いとプロセスが落ちます。症状・測定値・対処は
[プラットフォームの注記](./PLATFORM_NOTES.ja.md#スライディングウィンドウのバンドルgemma-4での-prefix-cache)にあります。

素の 2.49.40.260810 と素の 2.51.0.260929 で単体の再現プログラムを走らせ、結果は同じでした:
700 トークンの prefix は復元すると出力が変わり、1540 トークンでは segfault。素の 2.51.0 で
本サーバ経由で 1540 トークンの prefix を使うと、HIT はすべて壊れた出力になり、プロセスは落ちませんでした。2.50.0.260828 も同じコードです。
パッチを添えて Qualcomm へ報告済みで、2.51.0 では直っていません。**2.52.0.261104 で直りました**:
素の 2.52.0 で同じ再現プログラムを走らせると、700 トークンと 1540 トークンの prefix は、
復元しない dialog と同じ logits に復元されます。

## D7 — batching スケジューラの経路では、停止系列がスライディングウィンドウのダイアログを壊す

スライディングウィンドウの cache group を持ち、**per-layer embedding の無い**バンドル、つまり
continuous batching のスケジューラを通るもの(LFM3 など)が対象です。Gemma 4 のバンドルは per-layer
embedding を持つので従来の経路を通り、当たりません。

**症状**: 停止系列(`stop`)で終わったリクエストは普通に返ります。そのスロットの以後のリクエストは、
スロットを読み込み直すまで、すべて HTTP 500 `GenieDialog_query failed with status -1` になります。
サーバのログには `KV$ removal is disabled after longcontext triggers for CacheGroup swa_` と、続けて
`Removal of stop sequence tokens from KV cache failed` が出ます。長いプロンプトは要りません。統合テストで
停止系列を使う最初のリクエスト(20 トークンのプロンプト)だけで、次のリクエストが失敗します。

**原因**(ソースを読み、計装したライブラリで確かめた): この経路では、全 cache group の KV の帳簿を
スケジューラが持ち、ライブラリのもう一方の KV の帳簿は default のグループしか進みません。停止系列が
一致すると、ライブラリは一致したトークンをそのもう一方の帳簿で消そうとし、そこではスライディング
ウィンドウのグループは空のままです。グループはその食い違いを「窓の追い出しが済んだ」と取り違えて
拒みます。この失敗は `GenieDialog_reset` の後も残るので、以後の query もすべて失敗します。prefix 一致の
巻き戻しと通常の生成は、この経路ではその帳簿を通りません。通るのは停止系列の削除だけです。

**対処**: 当たるバンドルでは `stop` を送らないか、修正したライブラリ(prefix 一致の巻き戻しと同じく
スケジューラのスロットを巻き戻す)を使ってください。本プロジェクトはリビルド版にこの修正を入れています。
修正版では上のリクエストも、285 トークン(256 トークンの窓を越える)で止まった後も答え、LFM3 の 2 種類の
ビルドで統合テストが通ります。起きてしまったら `/v1/models/switch` でスロットを読み込み直してください。

## 手元の SDK を確認する

予算を十分に超えるリクエストを1本送り、続けて些細なリクエストを送ります:

```bash
python3 - <<'PYEOF'
import requests
B = "http://<host>:8080"
def chat(pad, mt):
    msgs = ([{"role": "system", "content": "filler " * pad}] if pad else [])
    msgs.append({"role": "user", "content": "Say hello."})
    r = requests.post(B + "/v1/chat/completions", timeout=300, json={
        "model": "genie-local", "max_tokens": mt, "temperature": 0, "messages": msgs})
    print(r.status_code, r.json().get("usage") or r.json())
chat(900, 4)   # 予算超過: 影響あり/なしのどちらの SDK でも成功する
chat(0, 4)     # 影響ありの SDK: HTTP 500、"GenieDialog_query failed with status -1"
PYEOF
```

2本目が失敗したら、その SDK には D1 があります。復旧はスロットの再ロード:
`POST /v1/models/switch {"slot": "<name>", "model_dir": "<同じモデル>"}`。

> [!NOTE]
> **二分探索はプロンプトではなく合計で行うこと。** 長いプロンプト + 小さい `max_tokens`
> で探ると、まともに振る舞う唯一の経路であるプレフィルしか動かしません —
> [D1](#単一コンテキスト長は予算を引き上げるが欠陥を消しはしない)で撤回した主張は、
> まさにこの誤りから生まれました。探索の合間には毎回スロットを再ロードしてください。

## ライブラリの選択

### 2.52.0 では — 素のライブラリを推奨の既定にする

素の 2.52.0 のライブラリは、2.51.0 でのリセットの欠陥の修正を引き継ぎ(2.52.0 では再現プログラムを
走らせ直していません)、grammar(リクエスト単位の API を含む)が使え、2.51.0 と違ってスライディング
ウィンドウのバンドルを正しく保存・復元できます(D6)。
open-genie-server 1.9.0 以降と組み合わせてください。残っているもの
(詳細は [2.52.0 で何が変わったか](#2520-で何が変わったか)):

- **D4**。2.51.0 と同じです。
- **concat 型のスライディングウィンドウの cache group が、そのグループのコンテキスト長を越えると崩れます**
  (LFM3 型のバンドル)。長いプロンプトで答えが変わることがあります。
- **graph の variant 切替でスライディングウィンドウのグループが追い出すとき、value のバッファを取り違えます**
  (Gemma 4)。logits がわずかにずれます。
- **graph の variant 切替のエラーを握りつぶす問題**(下の変更 2)。
- **D7**: per-layer embedding の無いスライディングウィンドウのバンドル(LFM3 型)で、停止系列で終わった
  リクエストの後、スロットが以後のリクエストをすべて失敗させます。

どれもソースでの修正があり、本プロジェクトはそれを入れたリビルド版で動かしています。リビルドすると、
バックエンドも用意しない限り grammar を失います([D3](#d3--リビルドしたライブラリには-grammar-が入らない))。
また、素の 2.52.0 のツリーは、インクルードパスを 1 つ足さないとビルドできません
([2.52.0 で何が変わったか](#2520-で何が変わったか))。SDK 自身の prefix キャッシュは、このサーバでは既定で
使いません。同じ節を参照してください。

### 2.51.0 では — 素のライブラリを既定にしてよい

素の 2.51.0 のライブラリには、リセットの欠陥(D1・D2・D5)が無く、grammar(リクエスト単位の
API を含む)があります。まだ残っているもの:

- **D4**: 制約つきの出力の末尾に終端トークンがテキストで付きます。クライアントで除くか、
  修正を入れてリビルドします。
- **D6**: スライディングウィンドウのバンドル(Gemma 4)では、ウォームアップする system prompt を
  約 600 トークン未満に抑えるか、そのモデルではウォームアップしません。
- **握り潰されるエラー**(下の変更 2): SDK はグラフのバリアント切り替えに失敗しても先へ進み、
  本当の理由ではなく `batch dispatch failed` を報告します。D1 が無くなったので害はありませんが、
  エンジンの失敗が読みにくくなります。
- **LUT 埋め込みのバンドルで prefix キャッシュが HIT したときの余分な BOS** —
  [MANUAL § Prefix KVキャッシュ](./MANUAL.ja.md#prefix-kvキャッシュ)の注記を参照。

2.51.0 をリビルドする価値があるのは、これらのためだけです。リビルドすると、バックエンドを
自分で用意しない限り grammar を失います([D3](#d3--リビルドしたライブラリには-grammar-が入らない))。
リビルドするなら、2.51.0 の OE makefile は 2.50.0 よりさらに多くのソースディレクトリが
抜けていることに注意してください([2.51.0 で何が変わったか](#2510-で何が変わったか))。

この節の残りは 2.49.x と 2.50.x の話です。

### 選択肢1 — 修正した `libGenie.so` を使う(2.49.x / 2.50.x で grammar が不要なら推奨)

SDK は Genie ライブラリの完全なビルド可能リファレンスソースを `examples/Genie/Genie/` に
OE/Android/x86 向け makefile とともに同梱しています(SDK 付属の
"Genie Sample Code Tutorial" 参照)。3つの変更で D1・D2 が消えます:

1. dialog のリセット時に、そのスロットの KV 位置をキャッシュグループの占有カウンタへ
   返す。現状のリセット経路はキャッシュのメモリをゼロ埋めするだけ。
   (リセット経路には、そのゼロ埋めすら空振りさせる順序バグもあり、先にこちらを直す必要がある。)— D1
2. 内部の「アクティブなグラフバリアントを切り替える」呼び出しの失敗戻り値を捨てるのをやめ、
   拒否されたときは古いテンソルのまま続行せず、本当の理由でバッチを失敗させる。— D1
3. リセット時に、スケジューラの KV 位置アロケータと高水位カーソルも巻き戻す。— D2

実機で検証済み: リビルドした `libGenie.so` は素のものと**まったく同じ 118 個の
`Genie*` シンボル**をエクスポートし(そのまま差し替え可能)、入れ替え後は予算を超えた
リクエストが**そのリクエスト自身だけ** `GENIE_STATUS_WARNING_CONTEXT_EXCEEDED` で
失敗し、スロットは健全なままになります。本サーバの実機統合テストは 3 失敗から
オールグリーンになります。

`env_config.json` の `GENIE_LIB_PATH` で指すか、SDK の `lib/` 内のファイルを置き換えます。
`GENIE_LIB_PATH` を使う場合、Genie は `libQnnSystem.so` を**自分自身の場所を基準に**
解決するので、指定するディレクトリには QAIRT ランタイムの他のライブラリも
揃っている必要があります(シンボリックリンクで構いません)。

**代償: grammar 制約デコーディングを失います**
([D3](#d3--リビルドしたライブラリには-grammar-が入らない))。バックエンドも自分で用意すれば別です。

### 選択肢2 — 予算内に収める

ライブラリを差し替えられない場合、または grammar が必要な場合:

- 毎リクエストで `prompt_tokens + max_tokens` を `コンテキスト長 − AR_N` 未満に保つ。
  **open-genie-server はこれを強制しません** — `max_tokens` を省略したときの既定値は
  残りの**宣言上の**コンテキスト(4096級)で、実際の予算をはるかに超えています。
  `env_config.json` に `DEFAULT_MAX_TOKENS` を設定し、予算に見合った `max_tokens` を
  明示的に渡してください。
- **単一コンテキスト長**でのエクスポートを推奨します。欠陥は消えませんが、予算が
  一桁上がります。短いリクエストのデコード速度は犠牲になります —
  [MANUAL § 複数のコンテキスト長で得られるもの](./MANUAL.ja.md#複数のコンテキスト長で得られるもの)参照。
- `-1` はそのスロットにとって致命的と扱う: `/v1/models/switch` で再ロードし、1度だけ再試行する。

## 2.49.1 で何が変わったか

バージョン番号が疑問を招くので記録しておきます。2.49.40.260810 に対して Genie のソースは
**12ファイル・+607/−192行、すべて engine 層**が異なります。公開 C API ヘッダは
バイト単位で同一、同梱 `libGenie.so` のエクスポートシンボルも同一なので、
そのまま差し替えられます。

変更のほとんどは、継続バッチングスケジューラが**スライディングウィンドウ注意(SWA)の
キャッシュグループ**(`longcontext.type: sliding-window` を持つ非デフォルトの
キャッシュグループを宣言したモデル)に対して KV 位置を割り当てる方法の作り直しです。
ほかに、実行時バッチサイズが 1 より大きいときのテンソル次元の解釈の修正が入っています。

**このページの欠陥にはどれも届かず**、当方の検証では観測可能な挙動の変化もありませんでした:

- 実機統合テストは両ビルドで全件同じ判定を返し、長文生成・長文プロンプト・
  関数呼び出しベンチマークのサブセットとも**生成テキストがバイト単位で一致**した。
- SWA の変更はすべて継続バッチングスケジューラ経路にある。モデルがそこへ到達するには
  SWA キャッシュグループを持ち、**かつ**スケジューラの起動条件を満たす必要があり、
  その条件は per-layer embedding を持つモデルなどを除外する。
- 手元のモデルはどちらかの理由で除外される: Qwen3 バンドルは SWA キャッシュグループを
  持たず、SWA を持つ Gemma 系バンドルは per-layer embedding も持つのでスケジューラに入らない。

**per-layer embedding を持たないスライディングウィンドウモデル**(2.49.1 が作り直した
コード経路)を動かすなら、これはあなたにとって意味のあるリリースですが、
**当方に測定値はありません**。試すなら1つリスクがあります: 新しいプレフィルチャンクの
クランプはチャンクを `容量 - (窓 - 1)` に抑えるため、SWA バッファが窓ちょうどの
サイズのバンドルでは、プレフィルが1発火あたり1トークンに潰れます。

## 2.50.0 で何が変わったか

2.49.1 よりはるかに大きなリリースですが、**D1〜D6 はすべてそのまま**です。

**差し替えはそのまま効きます。** 公開 C API ヘッダは 2.49.40.260810 と
バイト同一で、同梱の `libGenie.so` がエクスポートする `Genie*` シンボル 118 個も
一致します。本サーバを向け直すのに必要なのは `QAIRT_SDK_ROOT` と、対応する
Hexagon skel ディレクトリを `ADSP_LIBRARY_PATH` に入れることだけで、
再コンパイルも設定変更も要りません。

> [!CAUTION]
> **素のライブラリでテストが全件 PASS することは、D1・D2 が無い証拠にはなりません。**
> 本プロジェクトの統合テストは**素の** 2.50.0 で全件 PASS しましたが、
> 実行したのは単一コンテキスト長 `[8192]` / AR-128 のバンドルで、予算は 8064 トークン、
> どのテストもそこへ近づきません。同じボード・同じ回に複数コンテキスト長のバンドルへ
> 走らせた再現プログラムは、2.49.40 とまったく同じようにスロットに楔を打ちました。
> 統合テストの「素では3件失敗、パッチ版で全件 PASS」という以前の結果は、
> 予算が 384 で通常のリクエストがそれを越える**複数コンテキスト長**のバンドルでの測定です。
> **何を捕まえられるかはライブラリではなくバンドルで決まります。**

**本サーバに関して直っている点: ノードの生成順。** 2.49.x で `GenieNode`
パイプラインを組むとき、image encoder を text generator より先に生成すると、
text generator が weight sharing 済みのコンテキストを確保できず
`Could not create context from binary for context index = N : err 1002` で
失敗しました。本サーバは text-generator ノードを先に生成することでこれを回避しています。
2.50.0 では、SDK 同梱の `genie-app` にバンドル同梱のスクリプトを同梱の順序のまま
食わせても、そこで死なずに完走します。同じボードで数分差・空きメモリもほぼ同じ条件で実測:
2.49.40 は確保失敗のあと segfault、2.50.0 は2回とも完走。

> [!NOTE]
> **どの層が直したのかは特定できていません。** 検証では 2.50.0 のツリー
> (ライブラリ・QNN バックエンド・Hexagon skel)を丸ごと入れ替えており、
> リリースノートの Genie 節にも該当する記述はありません。
> **回避策はそのまま残します** — コストが無く、2.49.x では今も必要だからです。

**直っていない点。** D1・D2・D4・D5 は素の 2.50.0 で走らせ直し、対照として同時に
走らせた素の 2.49.40 と同じ判定(D1・D2 は文言まで同じ)で再現しました。
ソース側も一致しています — `qualla/dialog.cpp` のリセット順序、
`KVManager::clearSlotPositions()`、`SelfSpecDecDialog::reset()`、
`qualla/dialogs/basic.cpp` の終端トークン分岐は、いずれも変わっていません。

**知っておく価値のあるその他の変更**(いずれも当方では未計測):

- **DirectIO** — 大きいモデルの重みを DMA バッファへ直接読み込む任意機能
  (`qualla/engines/qnn-api/UDmaBufAllocator.cpp`、このビルドで新規)。
- **マルチテンソルの per-layer embedding** — per-layer 埋め込みテーブルを複数の
  テンソルに分割できるようになった(`qualla/embeddings/EmbeddingTable.cpp`、新規)。
- **エンジン層の修正**(SDK のリリースノート記載): 幅の広い prefill チャンクでの
  sliding-window キャッシュ、バッチ次元の解釈、コンテキスト分割10本以上でのグラフ順序、
  エンコーダ出力のパディングによる精度ずれ。
- **サンプラー設定が変換されなくなった。** 2.49.x はダイアログの `sampler` ブロックを
  ホワイトリスト経由で写し、その際に既定値も補っていました(`type` 未指定なら
  `"basic"`、`role` は常に `"primary"`)。2.50.0 は書かれたままエンジンへ渡します。
  当方のバンドルには影響がありません(greedy 判定を含め統合テストは全件 PASS)が、
  **サンプラーブロックを手書きするなら、これらをライブラリが補ってくれる前提を置かないこと。**

**D1/D2/D5 のためにリビルドする場合**、
[ライブラリの選択](#選択肢1--修正した-libgenieso-を使う249x--250x-で-grammar-が不要なら推奨)に書いた
3つの変更は 2.50.0 のソースにもそのまま当たります。追加で1点、同梱の OE makefile は
2.49.40 とバイト同一なので、**いくつかのソースディレクトリが依然として抜けており**、
さらに**新規の `src/qualla/embeddings/` の記述がまったくありません** —
追加しないと `EmbeddingTable.cpp` がリンクされません。**2.50.0 のビルドは未実施です。**

## 2.51.0 で何が変わったか

**リセットの欠陥 3 件を直しました。** 2.51.0.260929 には D1・D2・D5 がありません。
D1 と D2 は実測です: 素の 2.51.0 では、複数コンテキスト長のバンドルでも単一コンテキスト長の
バンドルでも再現プログラムが発火しません。D5 はソース論拠です
([D5](#d5--リセットが投機デコードのダイアログを壊す))。

**VLM パイプラインのコンテキスト超過も直りました。** 2.49.x と 2.50.x では、プロンプトが
コンテキストを超える VLM リクエストはスロットを楔にし、大きく超えるとプロセスが落ちます
([MANUAL § 視覚入力の上限](./MANUAL.ja.md#視覚入力の上限))。素の 2.51.0 では、同じ
Qwen3-VL-4B のバンドルで単体の再現プログラムを走らせると、超過は status 4
(`GENIE_STATUS_WARNING_CONTEXT_EXCEEDED`)で返り、リセット後のパイプラインは普通に答え、
17 フレームでもプロセスは落ちません。本サーバ経由ではまだ測っていません。

**本サーバにとっては差し替えるだけで済みます。** Genie の C API は 1.20.0 から 1.21.0 になり、
関数が 10 本増えて、消えたものはありません。素のライブラリの `Genie*` エクスポートは
118 個から 128 個になりました。2.49.40 でエクスポートしたバンドルは、作り直さずに 2.51.0 の
ランタイムでロード・実行できます。素の 2.51.0 での本サーバの統合テストの判定は 2.49.40 と
同じでした: Qwen3-1.7B のバンドルで全件 PASS、Gemma 4 E2B のテキストのバンドルでいつもの
既知の 1 件だけ FAIL。

**追加されたもので本サーバが使うもの:**

- `GenieDialog_setGrammar` は、ダイアログを作り直さずに grammar を差し替えます。
  本サーバは `response_format` と `structured_outputs` をこれに対応させています
  ([MANUAL § grammar制約デコーディング](./MANUAL.ja.md#grammar制約デコーディング))。
  起動時に Genie API の版をログに出します。

**追加されたもので本サーバがまだ使っていないもの:**

- `GenieNode_setValue` の `GENIE_NODE_PARAM_TEXT_GENERATOR_MAX_NUM_TOKENS` で、VLM の
  text-generator のトークン上限を実行ごとに設定できます。VLM スロットは今も、スロット全体の
  `VLM_SLOTS[].max_tokens` を使います。この経路には今も abort と stop シーケンスがありません。
- 段ごと(prefill / decode)の性能ポリシーと、直前の query が生成したトークン数。

**挙動の変更が 1 つ。** `SENTENCE_BEGIN` と `SENTENCE_CONTINUE` の query は prefill だけを
するようになりました。2.50 までは 1 トークンを sample してもいました。prefix キャッシュの
ウォームアップは `SENTENCE_BEGIN` を使います。D6 を直したライブラリで実機を見たところ、
HIT と MISS の出力の一致は 2.49.40 と同じかそれ以上でした。

**直っていないもの:** D3、D4、D6、LUT 埋め込みのバンドルで prefix キャッシュが HIT したときの
余分な BOS、握り潰されるグラフのバリアント切り替えのエラー
([選択肢1](#選択肢1--修正した-libgenieso-を使う249x--250x-で-grammar-が不要なら推奨)の変更 2)。
リセットは KV バッファ全体も消すようになり、リクエストごとに少し時間がかかります。
2.51.0 での量は測っていません。

**ライブラリをリビルドする場合**: 同梱の OE makefile には、2.50.0 で抜けていた 4 つの
ソースディレクトリに加えて、2.51.0 で新しく入った 5 つ(config manager、JSON schema validator、
engine のディレクトリ 3 つ)もありません。`make/Android.mk` が挙げているものと同じ集合を
足してください。共有ライブラリは `--no-undefined` でリンクされないのでリンクは通り、ボードの
`dlopen` で落ちます。

## 2.52.0 で何が変わったか

SA8255P(LV GVM)と QCS9075 の評価キットで、素の 2.52.0.261104 とそのソースからリビルドした
ライブラリを使って実測しました。「ソース」と書いた項目だけはソースに基づきます。

**D6 と、LUT 埋め込みのバンドルで prefix キャッシュがヒットしたときの BOS の重複を直しました。**
`GenieDialog_save` は cache group ごとに自分の件数・グラフの variant・(スライディングウィンドウの
グループなら)リングのスロットの順序を書き、`GenieDialog_restore` がそれを戻します。Gemma 4 E2B で
1,540 トークンの prefix を復元すると、復元しない dialog と同じ logits になります(2.51.0 では落ちた)。
LUT エンコーダは、トークン経路が以前からそうだったように、`SENTENCE_COMPLETE`・`BEGIN`・`REWIND` の
ときだけ BOS を足します。

**直っていないもの:** D3(ソース: grammar バックエンドは宣言だけで定義が無い)と D4(実測: このサーバ
経由で、grammar の終端の `<|im_end|>` がまだ応答の本文に入る)。グラフ variant のエラーの握り潰し
([選択肢1](#選択肢1--修正した-libgenieso-を使う249x--250x-で-grammar-が不要なら推奨)の変更 2)と、
variant 切替でスライディングウィンドウのグループを追い出すときの value バッファの取り違え(実測: KL 0.091。
修正したライブラリでは 0.003)も変わっていません。**D7**(batching スケジューラの経路で停止系列が
スライディングウィンドウのダイアログを壊す)も残っています。これを直す中で見つけたもので、毎回
dialog をリセットするこのサーバ経由では表に出ないものが 2 つあります: dialog を続けたとき、停止系列の
巻き戻しが本来より 1 トークン多く消すことと、KV の失敗が `GenieDialog_reset` の後も残ることです。

**concat 形式のスライディングウィンドウの cache group は半分しか直っていません。** リリースノートには
「continuous batching incorrectly handled windowed-path for concat format SWA cache groups」とあります。
2.52.0 はそうしたグループを batching スケジューラの windowed 経路から外し、グループの context 長より
手前の位置は正しくなりました。その先では、マスクが窓より古い位置をまだ開けています。LFM3 の 3 層の
プローブでは、FP32 参照との差が位置 383 までは 5〜8% に収まり、その後 44〜68% に広がります。LFM3 の
バンドル全体では、1,800 トークンのプロンプトで greedy の答えが変わります。修正したライブラリは全区間で
5〜7% を保ち、修正入りの 2.51.0 と同じ答えを返します。

**このサーバが追従しなければならなかった挙動の変更が 1 つあります。** `GenieSamplerConfig_setParam` は、
キーを 1 つ受けるたびにサンプラーの設定全体を検証し、通らなければそのキーを取り消すようになりました。
キーを 1 つずつ送ってカスタムサンプラーに切り替える(`type`、続いて `callback-name`)と、どちらの順でも
拒否されます。そのため 2.52 以降では、このサーバはサンプラーの設定を 1 つの JSON(キーは空)でまとめて
送ります。この形は 2.51.0 では普通の更新でも拒否されるので、古いライブラリには 1 キーずつ送ります。
1.9.0 より古い open-genie-server には 1 キーずつの経路しか無いので、2.52 のライブラリでは logprobs と
echo のリクエストに HTTP 400 を返します(1.8.0 で実測)。

**このサーバにとってはそのまま差し替えられ**、追加されたもののほとんどを使います。Genie の C API は
1.21.0 から 1.22.0 になり、関数は追加だけで、素のライブラリの `Genie*` エクスポートは 128 から 137 に
増えます。2.51.0 で書き出したバンドルは 2.52.0 のランタイムで読み込めて動きます。2.52 以降の libGenie では:

- 生成トークンの **logprobs は SDK が出します**(`GenieSampler_registerLogprobsCallback`)。
  [MANUAL § Logprobs](./MANUAL.ja.md#logprobs) 参照
- query の前ごとにプロファイルを消去します(`GenieProfile_clear`)
- `TOKENIZER_BACKEND` で libGenie の単体トークナイザ(`GenieTokenizer_create`)を使えます

**追加されたもののうち、既定では使わないもの: SDK の prefix キャッシュ**(`system_prompt_cache`)。
`bos-token` のあるバンドルでは一度もヒットしません。ヒットする場合は、ヒットすると greedy の出力が変わります。
復元そのものはバイト単位で正確です。SDK は system ターン全体を保存し、prefill のチャンク(AR)の倍数に
揃えないので、残りのプロンプトは、キャッシュなしのときとは違う位置から始まるチャンクで prefill されます。
測った Qwen3-0.6B のバンドルでは、それだけで答えが変わります。同じプロンプトを 700 か 823 トークンで
分けると、キャッシュなしでも答えが変わり、640 か 768 で分けると変わりません。system ターンをちょうど
768 トークンにすると、ヒット・ミス・キャッシュなしの logits はビット一致しました。保存する長さは、
設定でも API でも指定できません。どちらも `genie-app` と C API だけで再現しました。
`PREFIX_CACHE_BACKEND: "sdk"` で使えます。
[MANUAL § SDK の prefix キャッシュ](./MANUAL.ja.md#sdk-の-prefix-キャッシュqairt-252-以降)参照。

**それより古い libGenie は deprecated です。** 2.48 から 2.51 でもすべて動きます。2.52 より前に必要だった
経路(カスタムサンプラー経由の logprobs、ホスト側のトークナイザ)を使い、起動時に 1 回だけそう警告します。

**ライブラリをリビルドする場合**: OE の makefile は必要なソースディレクトリをすべて列挙するようになりましたが、
`src/qualla/engines` のインクルードパスが抜けていて、素のツリーはビルドが通りません
(`inference-types.hpp: No such file or directory`)。`INCLUDES` に `-I$(SRC_DIR_GENIE_ENGINES)` を
足してください。末尾に足すこと。エンコーダのディレクトリを dialogs より前に置くと、`Accuracy.cpp` が
別の `basic.hpp` を拾います。
