# プラットフォーム別の注意点

本ドキュメントに載っている実測値 — スループット、レイテンシ、どれだけデバイスに載るか、
どのモデルの組み合わせが同居できるか — は、**すべて1台の機体で測ったもの**です。
このページは、その機体が何であるか、そのうち**SoCの性質ではないもの**はどれか、
そして**あなたの機体がどうなのかをどう確かめるか**をまとめたものです。

> [!IMPORTANT]
> **あなたのデバイスがどう構成されているかは、当方にもこのドキュメントにも分かりません。**
> ゲストに割り当てられるメモリとストレージは Qualcomm のリリースによって異なり、
> イメージのビルド時に決まります(つまり変更もできます)。使える Hexagon NSP コアが
> いくつかは、**SKU のライセンスによって制限されます**。どちらも**ご自身のハードウェアで
> 確認するか、Qualcomm に問い合わせてください**。以下の数値は参考値であって、
> 既定値でも仕様でもありません。

出発点の数値も違います。

## プラットフォームによって変わるもの / それが何に効くか

| 変わるもの | 決めているもの | 本ドキュメントの何に効くか |
|---|---|---|
| **使える NSP コアの本数(1本か2本か)** | **SKU のライセンス**(Qualcomm が SoC の機能を SKU 単位で制限します) | [マルチテキストスロット](./MANUAL.ja.md#マルチテキストスロット)の記述すべて。1本しか使えない場合、`TEXT_SLOTS` の `device_id: 1` は割り当て先が存在せず、1.31倍という並列性能の数値も当てはまらず、2モデルの同居もできません(1コアには1モデル。[2つのモデルを同時にロードする](./MANUAL.ja.md#2つのモデルを同時にロードする)) |
| **ゲストに割り当てられる RAM・ストレージ** | イメージをビルドした人。ビルド時に変更可能 | そもそもどのバンドルがロードできるか、1本目の隣に2本目が入るか、`err 1002` にどれだけ出会うか |
| **どのファイルシステムに書き込めるか、システムの Python に何が入っているか** | イメージをビルドした人 | サーバと依存パッケージをどこに入れられるか — [デバイスへのインストール](#デバイスへのインストール) |
| **DSP のマッピングを支える SMMU ページテーブル用プール** | ボードの構成。この機体ではハイパーバイザが持ち、16 MB。**ゲストからは見えない** | **`err 1002` の実際の天井**、したがって何スロット同居できるか — [`err 1002` の予算はどこにあるのか](#err-1002-の予算はどこにあるのか) |
| **ベアメタルかゲストか** | ボードの構成 | サブシステムリスタート。ハイパーバイザ上ではゲストから `/sys/class/remoteproc` に届かないことがあり、その場合、固まった cDSP の復旧はボードの電源サイクルだけになります |
| **QAIRT のバージョンと ABI** | 利用者 | どの SDK 欠陥を抱えるか([QAIRT バージョン別の問題点](./QAIRT_VERSIONS.ja.md))、サーバがどのライブラリディレクトリから読むか([Androidで動かす](./MANUAL.ja.md#androidで動かす)) |
| **モデルバンドル** | エクスポートした人 | コンテキスト長の変種と AR 長が実際に使えるトークン予算を決め、量子化のレシピが `<tool_call>` マーカーの化けのような欠陥の有無を決めます。**同じモデルでもエクスポート設定が違えば挙動は同じになりません** |

Qualcomm 自身のドキュメントも2本目のコアを同様に扱っています — どの HTP デバイスで
モデルを実行するかの選択は、**Auto プラットフォーム(SA シリーズ)向けの機能**として、
拡張ライブラリ経由で説明されており、あらゆるターゲットが備えているものとしては
書かれていません。

## 自分のデバイスがどうなのかを確かめる

**NSP コア。** `device_id: 1` のスロットを設定してサーバを起動してください。
両方のスロットが ready になるか、デバイスの作成に失敗するかのどちらかです。
**事前に問い合わせる確実な方法はありません** — 特に `/dsp/image/dsp/cdsp1` の有無は
**ゲストイメージが何を見せているかであって、ライセンスが何を許しているかではない**ので、
手がかりではあっても答えではありません。

```bash
# 1コアにつき1スロット。2本目が割り当てられなければ起動時に分かります。
# ロード順の制約は MANUAL.ja.md「マルチテキストスロット」を参照。
curl -sS http://<device>:8080/v1/server/status | python3 -m json.tool
```

**メモリとストレージ。**

```bash
grep -E 'MemTotal|MemAvailable' /proc/meminfo
df -h <モデルを置いているファイルシステム>
```

**インストールできる場所。**

```bash
mount | grep -E ' on / | on /home | on /data '   # / に "ro" があれば、システムの site-packages は読み取り専用
python3 -m pip --version                         # "No module named pip" なら venv を使う
```

**サブシステムリスタート。** `ls /sys/class/remoteproc` — 空であれば、ゲスト内から
cDSP を再起動することはできず、復旧手段は電源サイクルです。

**それ以外 — 既定値がいくつか、あなたの SKU が何を許可しているか、ゲストがどう
サイジングされたか。** これらは **Qualcomm が答えるべきこと**で、答えはボードと
リリースによって変わります。このページから推測せず、**問い合わせてください**。

## デバイスへのインストール

**この機体では、サーバと依存パッケージを `/home/root` の下の venv に入れる必要があります。**
好みの問題ではありません。ゲストのルートファイルシステムは読み取り専用でマウントされ、
システムの `python3` には pip が無いので、**pip が動けるのは、書き込めるファイルシステムに作った venv の中だけ**です。

ゲストで書き込める場所:

| パス | 書き込み | |
|---|---|---|
| `/`(`/usr` とシステムの `site-packages` を含む) | **不可** | ext4 を `ro` でマウント、1.5 G |
| `/home` と `/data` | **可** | **1つ**の 29.4 G の ext4 を両方にマウントしているので、`/home/root` と `/data/root` は同じディレクトリです。モデル・SDK・venv はすべてここに置きます |
| `/tmp`・`/var`・`/run` | 次の起動まで | tmpfs です。RAM 上にあって再起動で消え、固まった cDSP の復旧はボードの電源サイクルです。venv を置く場所ではありません |
| `/persist` | 可 | イメージ自身の設定(`/etc/bluetooth`・`/etc/usb`・`/etc/build.prop` の実体)。自分のファイルを置く場所ではありません |

システムのインタプリタは `/usr/bin/python3` の Python 3.10.14 です。`python3 -m pip` は
`No module named pip` で失敗しますが、`venv` と `ensurepip` はあり、venv にはそれで足ります:

```bash
cd /home/root
python3 -m venv .venv                                    # ensurepip が venv の中に pip を入れる
.venv/bin/pip install 'open-genie-server[logprobs,vlm]'  # クローンからなら '.[logprobs,vlm]'
.venv/bin/genie-server --config env_config.json
```

パッケージをインストールせずにクローンから動かす場合も、venv のインタプリタを使います:
`.venv/bin/python3 genie-server.py`。venv は activate せず、venv の実行ファイルをパスで呼んでください —
`adb shell` は呼ぶたびに新しいシェルを起動するので、activate は次のコマンドに引き継がれません。

**ゲストが PyPI に出られない場合。** この機体のゲストはホスト経由でネットワークに出られますが、
それはこの機体の性質です。経路が無ければ、出られるマシンで wheel を集め
(`--platform` を付けると、pip は自分が動くマシンではなく指定したプラットフォーム向けの wheel を選びます)、
ディレクトリごとコピーして、そこから入れます:

```bash
# ネットワークに出られるマシンで
pip download 'open-genie-server[logprobs,vlm]' -d wheels \
    --python-version 3.10 --only-binary=:all: \
    --platform manylinux2014_aarch64 --platform manylinux_2_28_aarch64
# wheels/ を /home/root/wheels にコピーしてから、デバイスで
.venv/bin/pip install --no-index --find-links=/home/root/wheels 'open-genie-server[logprobs,vlm]'
```

`--python-version` はゲストの `python3 --version` に合わせ、manylinux のタグはゲストの glibc が
受け付けるものを並べてください(`getconf GNU_LIBC_VERSION`。この機体は 2.35 なので上の2つとも)。
**`manylinux2014_aarch64` だけでもダウンロードは成功しますが、黙って古い版に解決されます** —
執筆時点では pillow が 12.3.0 ではなく 12.2.0 に、`huggingface_hub`(`tokenizers` の依存)が、
`manylinux_2_28` の wheel しか無い `hf_xet` を必要としない古い版になりました。

## `err 1002` の予算はどこにあるのか

`err 1002` が何をするかは
[2つのモデルを同時にロードする](./MANUAL.ja.md#2つのモデルを同時にロードする)にあります。
ここに書くのは、**この機体でそれが何であるか**、そして**そのほとんどが SoC の性質ではない**
ということです。

**これは DSP 側の確保の失敗ではありません。** SDK 自身のログを有効にすると
(`GENIE_LOG_LEVEL: "info"`。[設定](./MANUAL.ja.md#設定-env_configjson))、
通常見えている行の手前に3行出ます:

```
<E> fastrpc memory map for fd: 129 with length: 312475648 failed with error: 0x1
<E> Mapping buffer fd 129 to FastRpc failed on domain 3
<E> Failed to map weights buffer on host, err 3
<E> Failed to map shared weights for contextId 9 on deviceId 0, coreId 0, pdId 0, err: 1002
```

コンテキストの**共有重みバッファ**([小さいモデル1種類を何本まで載せられるか](./MANUAL.ja.md#小さいモデル1種類を何本まで載せられるかそして1本いくらか)のバンドルでは 298 MiB)を、
**ホスト側から** DSP の保護ドメインへマップできなかった、というだけです。
`err 1002` は QNN の汎用のメモリ確保エラーコードなので「DSP のメモリが尽きた」と読めますが、
**失敗したのはマッピング**です。ゲストのカーネルも同じことを別の言葉で言い、
**ハイパーバイザが顔を出すのはこの層**です:

```
virtio-mmio ...: invalid smmu da 0
virtio-mmio ...: can't get map da
adsprpc: genie-server: hfastrpc_mem_map: failed to map fd 129, len 0x12a00000, ... err -14
```

**この機体で尽きているのは、ハイパーバイザが持つ固定サイズの SMMU ページテーブル用プール**
(16,384 KB)で、**DSP のメモリでもゲストのメモリでもありません** —
失敗の瞬間、システムメモリは 10.9 GB 空いていました。

**この消費はゲストからは見えません。** ゲストの `/proc` のどこにもその分は現れず、
だからこそマニュアルは長らく、Linux 側で測れる何からも `err 1002` を予測できませんでした。
**ハイパーバイザ側 —— このボードでは QNX —— から見る必要があります。**
そこではプールとその使用量が報告されます。実測:

| 状態 | QNN コンテキスト | プール使用量 |
|---|---|---|
| 電源サイクル直後、モデル無し | 0 | **3,332 KB** |
| 4スロット | 8 | **11,524 KB** |
| 6スロット | 12 | **15,620 KB** |

[小さいモデル1種類を何本まで載せられるか](./MANUAL.ja.md#小さいモデル1種類を何本まで載せられるかそして1本いくらか)の**バンドルでは1スロットあたり 2,048 KB** です。
おかげで上限が経験則ではなく**算術**になります: `(16,384 − 3,332) / 2,048 = 6` スロットで、
**7本目のスロットは残り 764 KB に対して 2,048 KB を要求して入りません**。
どちらの数値も、その掃き出しが外から測った結果と一致します。

> [!NOTE]
> *(訂正)* 以前の版は、このプールは **QNN コンテキスト1本あたり 1,024 KB** で課金され、
> したがって上限はバイト数ではなくコンテキスト単位だと書いていました。これはこのバンドル1つでだけ成り立つ値です。
> 課金は**スロットがマップするアドレス空間**に従います。4 KB ページのページテーブルは
> DSP のアドレス空間 2 MiB ごとに 4 KB を使い、プールはそれを 256 KB 単位で払い出します。
> 同じ 0.6B を複数コンテキスト長でエクスポートしたバンドルは、**同じ2本の QNN コンテキスト**を作って
> **4,864〜5,120 KB** かかります。6つのグラフが、I/O テンソル・spill-fill・op data を、さらにロード中だけは
> それら全部を合わせた大きさの I/O バッファ1本(2本目のコンテキストで 732 MiB)を、多くマップするからです。
> 下のアドレス空間のマップから 2 MiB の領域を数えると、マップを読めた場合にはプールの使用量と 256 KB 単位で一致します。

**上限は1つではなく2つあります。** 上のプールは、全体でどれだけマップできるかの上限です。
それとは別に、**DSP の保護ドメインはそれぞれ 4 GiB のアドレス空間を持ち**、
マッピングはどれもその中に連続した場所を見つける必要があります:

- マッピングは**サイズ以下で最大の2の累乗の倍数**から始まり(298 MiB の重みバッファなら 256 MiB 境界、
  732 MiB のバッファなら 512 MiB 境界)、入る所のうち**最も低いアドレス**に置かれます。
- このため空間が**断片化**します。複数コンテキスト長の 0.6B を1つのコアに2スロット載せると、
  そのドメインのアドレス空間が 1,347 MiB 空いているのに失敗します。512 MiB 境界から 732 MiB 続く穴が
  1つも無いからです —— 1本目のスロットのロード中のバッファが解放され、その場所をそのスロット自身の
  262 MiB の I/O バッファが取っていました。
- そのときプールには余裕がありました。ハイパーバイザはアドレス空間の枯渇とプールの枯渇を別々に報告しますが、
  ゲストにはどちらも同じ `err 1002` として届きます。

**どの保護ドメインに載るかは、本数ではなく予算で決まります。** コンテキストは pd 0、pd 2、pd 4 … の順に、
**予算にまだ余裕がある最初のドメイン**へ入ります。予算は**ドメインの番号ごとに1つで、両方のコアが共有**し、
コンテキストには、context binary のメタデータにある**共有重み + グラフの I/O テンソル・spill-fill バッファ・
op data の合計**が課金されます。24回の起動で、すべての配置が 3,403,453,184〜3,503,631,616 バイト
(約 3.4〜3.5 GB)の予算で説明できます。CL1024 のバンドルだけを載せるとこれは
「コンテキスト 1〜7 が pd 0、8本目が pd 2、9本目が再び pd 0、10本目以降が pd 2」になり、
以前の版はこの並びを規則そのものとして書いていました。*(訂正: バンドルを混ぜるとこの並びは崩れます ——
複数コンテキスト長の2スロットに CL1024 を1スロット足すと、5本目のコンテキストが pd 2 に入ります。)*

**これがマニュアルにあるロード順の規則の機構です。** 片方のコアの CL1024 5スロットを先に書くと、
コンテキスト 1〜7 がそのコアの pd 0 を埋め、9本目は予算の上では再び pd 0 に来ますが、
その 298 MiB の重みはそのドメインのアドレス空間に空いた 256 MiB 境界を見つけられません ——
そのときプールには 4.6 MB の空きがあります。もう片方のコアのスロットを先に書くと、
その2本のコンテキストが pd 0 の予算を一部使うので、最初のコアの pd 0 に入るのは7本ではなく5本になり、
9本目が入ります。片コアに4スロット + もう片方に2スロットは、9本目がもう一方のコアへ行くので成功します。
そして予算がコアをまたいで共有されるので、**あるコアのスロットが、もう片方のコアのコンテキストの行き先を動かします**:
1つのコアに単独では同居できない複数コンテキスト長の 0.6B 2スロットも、もう片方のコアの CL1024 スロットを
先にロードすると載ります。2本目のスロットの大きい方のコンテキストが pd 2 へ押し出されるからです。
1つのコアに載せる同じ3スロット(CL1024 ×2 と複数コンテキスト長 ×1)は、順序によって載ったり失敗したりします。
**この4つの結果は、測る前にこれらの規則から予測し、すべて一致しました。**

> [!WARNING]
> **プールは1回のブート内での高水位であり、戻りません。**
> サーバを止めても下がらず、再ロードしても上がらず、**電源サイクルでのみ基準値に戻ります**。
> マニュアルが「同居の判定は電源サイクル直後の初回起動で行う」と言っているのはこれが理由で、
> **失敗した起動が見た目より悪い**のも同じ理由です。`err 1002` で失敗した起動も
> ページテーブルを返さないので、**繰り返すとプールを削り切り**、最後は `err 1002` ではなく
> **`Failed to create device: 14001`** で起動しなくなります。そうなるとサーバのプロセスは
> **`SIGKILL` でも終わらない**ことがあり、ファイルシステムを掴んだままなのでゲストの再起動も完了せず、
> **復旧はボードの電源サイクル**になります。

**以上はボードの構成が違えば当てはまりません。** ページテーブルのプールはハイパーバイザのもので、
その大きさはイメージをビルドした時点で決まっており、ハイパーバイザの無いプラットフォームでは
勘定はまったく別の場所にあるはずです。**移ると考えてよいのは問題の形だけ**です —
`err 1002` がぶつかる予算は**マッピングの予算**(ページテーブルと DSP のアドレス空間)であり、
**コンテキストの本数ではなくマップする量に従い**、**ゲストからは見えない**。自分のプラットフォームでどこを見ればよいかは Qualcomm が答えるべきことです。

## 本ドキュメントの他の記述をどう読むか

以下はいずれも上記の機体での実測値です。**その機体については正直な数値ですが、
構成の違う機体については何も語りません**:

- **2本目のスロットによる約1.31倍のスループット向上**と、残りがどこへ消えたかを
  説明する prefill/decode の内訳 — [マルチテキストスロット](./MANUAL.ja.md#マルチテキストスロット)
- **どのモデルの組み合わせが同居できるか**、そして**その答えが合計サイズではなく
  「どちらを先にロードするか」で決まる**こと —
  [2つのモデルを同時にロードする](./MANUAL.ja.md#2つのモデルを同時にロードする)
- **`err 1002` の閾値**(2本目のコアでの確保が1本目の側にも効くことを含む)、および
  [その予算がどこにあるのか](#err-1002-の予算はどこにあるのか) —

  [QnnHtp.poll](./MANUAL.ja.md#qnnhtppoll-はcpuを約260使うがここでは何の得も無い)
- **36回のホットスワップの実測**と、その成否がモデルの組み合わせで決まらなかったこと —

- **モデルごとの挙動** — `<tool_call>` マーカーの化け、トークン予算、テンプレートの系統。
  これらは**特定のバンドルの性質**であって、SoC の性質でもモデル名の性質でもありません
